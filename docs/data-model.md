# AI 데이터 모델

스키마 원본은 `pipeline/db/ai_schema.sql`입니다. 다른 서비스의 DB를 직접 수정하지 않습니다.

### ai_db (ai-svc)

| 테이블 | 소유 | 용도 | 핵심 컬럼/관계 |
|---|---|---|---|
| wiki_schemas | ai-svc | 워크스페이스·사용자별 Wiki 생성 규칙 | active 스키마는 소유 범위당 최대 1개(부분 unique index) |
| document_derived_state | ai-svc | 문서 파생물 stale 추적 | `document.edit.event` consumer가 갱신 |
| wiki_pages·document_wiki_links·wiki_page_links | ai-svc | Wiki 현재 상태와 문서/페이지 관계 | 페이지는 워크스페이스 공유 자산으로 `(workspace_id, page_type, slug)` unique(ADR 0033). `user_id`는 마지막 편입 요청자 귀속 정보다. 사용자별 중복 행이 남은 DB는 스키마 적용이 실패하므로 위키 데이터를 초기화한 뒤 배포한다. DB 밖 document ID는 논리 참조. 소스 페이지 slug는 웹·MCP 모두 `slugify(document_id)`이며, 예전 MCP 편입이 문서 ID 그대로 남긴 slug는 스키마 적용이 고친다(같은 문서의 웹 소스 페이지가 이미 있으면 그대로 둔다). 사람이 고친 본문은 `ops/{operation_id}.md`·`.json`(`artifact_type: "manual"`)으로 남고 `markdown_uri`가 그 본문을 가리킨다. 수동 기여의 `added_links`·`removed_links`가 본문 `[[slug]]` 차이를 `wiki_page_links`에 반영한다. 소스 → 개념 자동 링크(`source_mentions_concept`)는 기록하지 않고 파생한다(ADR 0042 결정 5). 문서 D의 소스 페이지 → 개념 P 링크는 P의 `document_wiki_links`(`extracted_concept`)에 D가 있고(재생 결과 D의 유효한 직접 개념 기여나 살아 있는 항목·근거가 있다) 두 페이지가 활성이며 D가 `wiki_source_tombstones`에 없을 때만 있다. 문서 연결과 이 링크는 `sync_source_concept_links`가 같은 트랜잭션에서 모든 페이지 최종 상태를 쓴 뒤 맞춘다(편입·기존 개념 갱신, lint 분리·합치기·승격, 복원, 재조정). 사람이 source 본문에 쓴 `[[slug]]`는 `wiki_source_manual_links`(`from_page_id`·`to_page_id`·`present`)에 수동 지원·삭제로 따로 남고, 수동 삭제가 자동보다 우선한다. 페이지 삭제는 논리 삭제라 이 의도 행은 지우지 않고, 페이지가 다시 살아나면 그대로 적용된다. 합치거나 지운 페이지의 방향 전환은 두지 않는다(ADR 0042). 지운 페이지를 가리키는 링크는 잇지 않는다. 기여 원장·revision은 document-svc가 소유한다([adr/0031](adr/0031-manual-wiki-contributions.md)) |
| wiki_page_entries | ai-svc | 개념 페이지 하위 항목의 조회용 사본(ADR 0042) | PK `(workspace_id, entry_id)`, `page_id`(집, `wiki_pages` FK CASCADE)·`name`·`definition`(같은 항목 쌍 판정 입력)·`parent_entry_id`(NULL이면 페이지 바로 아래)·`block_refs`(근거 블록, 전역 형식)·`position`(본문 목록 순서)·`slugs`·`aliases`·`tags`(하위 항목이 된 개념의 원래 slug·별칭·태그. 원래 slug는 다시 편입할 때 같은 항목을 찾는 정체성이고, 별칭·태그는 부모 페이지에 섞지 않는다. 기여마다 더한다). 원본은 기여 JSON의 `entry_changes`이며 복구 재생(`rebuild_page`) 결과로 페이지마다 지우고 다시 쓴다. 편입은 새 항목을 더하고, 이미 있는 항목에는 근거 블록만 더한다. 다른 페이지에서 옮겨 온 항목은 집만 바뀐다. 삭제한 페이지의 항목은 함께 지운다. 참조는 이 테이블이 아니라 `wiki_page_links`의 `entry_reference` 간선이다 |
| wiki_page_entry_references | ai-svc | 하위 항목 참조의 조회용 사본(ADR 0042) | PK `position`, UNIQUE NULLS NOT DISTINCT `(page_id, entry_id, parent_entry_id)`, `page_id`(참조하는 페이지, FK CASCADE)·`target_slug`(집 페이지)·`name`·`parent_entry_id`·`position`. 간선은 페이지 쌍 하나라 본문 목록을 다시 그리려고 항목별로 둔다. 원본은 참조하는 페이지 기여의 `entry_reference` 링크이며 편입이 더하고 복구 재생이 페이지마다 다시 쓴다. 수동 편집·lint 복구가 `entry_reference` 간선을 지우면 같은 트랜잭션에서 사본도 지운다(`entry_id`가 없으면 그 페이지 쌍의 참조 전부) |
| source_blocks·source_block_snapshots | ai-svc | 문서 block 텍스트·문서 내 순서·줄 범위, block 집합을 만든 편입 입력 Markdown의 SHA-256 | 복합 PK `(block_id, document_id)`. 영구 `block_id`는 문서 순서가 아니므로 `position`(1부터) 순으로 조회한다. `line_start`·`line_end`는 입력 Markdown을 `\n`으로 나눈 1-based 양끝 포함 값이며 채팅 문서·기존 행은 null. 스냅샷 해시는 블록과 같은 트랜잭션에서 갱신해 편입 실패 시 직전 성공 값을 유지한다 |
| wiki_source_tombstones | ai-svc | 휴지통으로 옮긴 원본 문서 표시 | `document_deleted` 처리가 기록(`deleted_at`은 삭제마다 갱신)하고 해당 문서의 ingest 완료(웹·MCP 공통 `apply_ingest_outputs`)가 지운다. 로그 되돌리기는 표시된 문서의 source 페이지·문서 링크를 되살리지 않는다. post_ingest는 `deleted_at`이 부모 ingest run 생성 시각보다 늦으면 의미 클러스터 근거를 쓰지 않는다(복구 뒤 다시 만든 run은 통과) |
| pipeline_runs | ai-svc | pipeline 실행 상태 | Spring이 만든 `run_id`, `user_id`·`workspace_id` 보존. ingest manifest의 `post_ingest.status`는 `running/retrying/ready/needs_review` 품질 진단 상태를 보존(단계가 끝까지 실패해도 되돌리지 않고 `needs_review`와 `error`를 남긴다, ADR 0044) |
| mcp_wiki_ingest_runs·mcp_wiki_source_blocks·mcp_wiki_windows·mcp_wiki_window_submissions | ai-svc | I9의 미공개 snapshot/window intake | run이 immutable Document source version/hash/표시 이름(`source_display_name`, SOURCE 페이지 제목용)과 server UUID snapshot mapping, actor workspace/user/grant/client/generation/provenance, configured TTL/active storage를 소유한다. block PK는 `(snapshot_id,block_id)`, ordinal도 snapshot 안에서 unique다. window는 ordered block hash와 exactly-once submission을 보존한다. 상태는 `ACTIVE_WINDOWING`, `READY_TO_FINALIZE`, `AWAITING_WEB_APPROVAL`, `EXPIRED`, `CANCELLED`, `INVALIDATED`이며 awaiting도 document active-ingest fence와 TTL/cancel/purge 대상이다. wiki page/body/contribution/publication outbox를 만들지 않는다. `pipeline_runs`와 같은 document advisory fence로 active ingest를 배타화한다. |
| mcp_pdf_conversions·mcp_pdf_conversion_submissions | ai-svc | MCP 외부 AI PDF 변환 세션 | 세션이 actor workspace/user/grant/client/generation, 원본 document_id·source_key·source hash, 멱등 키와 조립 결과 hash를 소유한다. 전처리 진행은 converter journal(`ai_task_runs`, `mcpconvert:*`)과 `tmp/convert/mcp/` 묶음에서 읽는다. 제출은 창당 1회이며 기존 복원 검증 결과와 그 제출이 만든 재시도 창 block id(`response.followup_block_ids`)를 함께 둔다. `final_markdown_hash`는 조립 결과 `final.json`(`tmp/mcp-convert/`, tmp/ 7일 lifecycle) 바이트의 hash다. 문서·wiki를 만들지 않으며 원본 연결 `create_document` 제안은 조립 결과 key·hash가 같을 때만 받는다. 워크스페이스·사용자 삭제 대상이다. |
| mcp_wiki_drafts·mcp_wiki_lint_source_blocks | ai-svc | I9 immutable INGEST/LINT full preview | PK `draft_id`; INGEST는 existing run FK를, LINT는 nullable run과 자체 actor/state/TTL을 쓴다. owner, command hash, source/target snapshots, normalized closed operations/evidence, calculation inputs(INGEST는 웹 반영 전 공개 상태와 반영 effect), complete ordered changes, public-state/draft hash와 exact preview를 보존한다. | mcp_wiki_draft_idempotency | ai-svc | start/submit/finalize exact response replay | actor workspace/user/grant/client, tool, document 또는 run/window scope, key가 복합 PK다. verified canonical request hash와 최초 exact response만 저장하며 다른 body는 conflict다. terminal lifecycle fence가 replay보다 먼저 적용되고 user/workspace purge가 삭제해 late command가 preview를 되살리지 않는다. |
| document_quality_reviews | ai-svc | 문서별 최신 편입의 post_ingest 품질 상태 | 편입 성공 커밋이 행을 그 run으로 갈아끼우고(상태·평가 비움) post_ingest가 같은 run일 때만 `status`·`evaluations`를 채운다. pipeline run이 없는 MCP 편입은 행을 지워 평가 전 상태로 둔다. lint 검색 품질 보고는 이 행만 읽는다. `ingest_run_id`가 `pipeline_runs`를 참조해 run이 지워지면 함께 지워진다 |
| wiki_pending_contributions | ai-svc | 원장 반영 대기 편입 기여 | 편입 커밋이 기여 JSON을 남긴 개념 페이지마다 쓴다. document-svc 원장에 오르기 전에 같은 페이지를 원장으로 다시 그리는 작업(재편입·참조 정리·lint)이 원장 뒤에 붙이고, 원장에 오른 행은 그때 지운다. 반영 전에 문서를 휴지통으로 옮기면 꺼진 기여로 본다. 원장과 대조할 때 AI 삭제 이벤트가 늦어도 document-svc가 알린 원본 삭제(`source_document_deleted`)나 휴지통 이동이 끈 기여(`deactivated_by_source_deletion`, 바로 복구한 문서 포함)는 꺼진 것으로 맞춘다. 복원(`RESTORE`) 대기 행은 순번이 같으면 `linked_by_operation_id` null(예전 API에서 옮긴 값)을 원장의 연결 lint ID와 같은 것으로 본다. 작업 취소 되돌리기 대상이며 `wiki_pages` 행이 지워지면 함께 지워진다 |
| wiki_publications·wiki_publication_objects·wiki_publication_outbox | ai-svc | 불변 위키 본문의 공개 경계와 결과 전달 | `PREPARED` 객체는 현재 작업과 재전달이 계속 쓸 수 있고 `COMMITTED` 본문·결과·outbox는 정리하지 않는다. 작업 journal이 성공적으로 rollback돼 terminal이 된 미공개 작업은 즉시 `ABANDONED`로 fence한다. maintenance worker는 `AI_WIKI_PUBLICATION_CLEANUP_GRACE_SECONDS`가 명시된 경우에만 기동 직후와 10분마다 grace를 지난 미공개 작업을 본다. `PREPARED`는 업로드된 객체가 있고 같은 operation의 task journal/실행 중 pipeline owner가 없으며 workspace concept lock과 publication lock을 모두 획득한 경우에만 `ABANDONED`를 먼저 commit한다. 따라서 시간만으로 실행 중 writer를 죽이지 않으며, process-death 뒤 grace 안의 재전달과 journal/pipeline recovery는 계속 보존된다. 그 뒤 현재 page, pending contribution, committed result, pipeline manifest, task command/result, 아직 되돌리지 않은 journal 변경이 참조하지 않는 `ops/*.md|json`만 지우고 legacy fixed key는 보존한다. 삭제 실패나 삭제 뒤 DB rollback은 `deleted_at`을 남기지 않아 다음 주기에 멱등 재시도하며 publication tombstone은 operation 재사용을 막는다. 운영 배포에는 0 이상의 grace 초 값을 별도로 결정해야 하고, 미설정이면 destructive cleanup은 꺼진다. |

`wiki_publication_outbox.state='sent'`는 broker ACK만 뜻한다. maintenance command worker는 기존 5초 retry cadence와 20건 batch로 body-free Document receipt를 조회하고, 정확한 scope·publication·operation·event alias·kind·outcome·reference hash·commit time이 모두 맞을 때만 `receiver_disposition`과 `receiver_confirmed_at`을 기록한다. receipt 누락·timeout·잘못된 응답은 UNKNOWN으로 두고 같은 event를 재전달한다. `REJECTED_CONFLICT/STALE_RESTORE`는 성공이 아니며 재전달을 멈추고 운영자 조치가 필요한 durable conflict로 남아, 해당 pending contribution을 사용한 rebuild를 차단한다. 보고 쿼리: `SELECT event_id, publication_id, state, attempts, receiver_disposition, receiver_rejection_reason, receiver_confirmed_at FROM wiki_publication_outbox WHERE receiver_disposition IS DISTINCT FROM 'ACCEPTED'`.

Concept 본문 persistence는 ingest와 lint `materialize=true`가 같은 워크스페이스 PostgreSQL transaction advisory lock(`concept-persistence:{workspace_id}`)을 사용해 최종 object read-modify-write부터 DB commit까지 직렬화한다. 편입에 넘기는 기존 개념 목록 캐시도 워크스페이스 키(Redis `wiki:concept-index:{workspace_id}`, TTL 300초)다. 문서 편입의 개념 판정은 워크스페이스 `concept_write_lock`을 잡은 뒤 이 캐시를 거치지 않고 DB에서 다시 읽은 목록으로 한다.

개념 페이지 하위 항목(ADR 0042)은 기여 JSON(`ops/{operation_id}.json`)의 `entry_changes`를 `sequence_revision` 순으로 재생해 만든다. 항목 id는 워크스페이스 안에서 고유하다.
- `{"op": "add", "entry_id", "name", "definition", "parent_entry_id", "anchor_reference_ids", "evidence_claim_ids"}`: 없으면 만들고, 있으면 근거만 더한다. 이름·정의·상위 항목은 처음 추가한 기여를 따른다. 근거는 개념 근거와 같은 전역 형식(`{document_id}:{block_id}`, `{operation_id}:{evidence_id}`)으로 바꿔 둔다.
- `{"op": "move", "entry_id", "parent_entry_id"}`: 상위 항목만 바꾼다. 없는 항목이거나 자기 아래로 옮기면 무시한다.
- `{"op": "remove", "entry_id"}`: 항목과 그 아래 항목을 지운다.
- 상위 항목이 남지 않은(그 기여를 되돌린) 항목은 페이지 바로 아래로 올린다.
- 다른 페이지 항목을 가리키는 참조는 참조하는 페이지 기여의 링크(`links`, lint·수동은 `added_links`·`removed_links`)로 남긴다. `{"source": "concept:{참조 페이지}", "target": "concept:{집 페이지}", "relation": "entry_reference", "entry_id", "name", "parent_entry_id"}`이다. 재생은 항목과 상위 위치(`parent_entry_id`, NULL은 페이지 바로 아래)마다 따로 남긴다. 같은 페이지 안의 다른 상위 위치도 참조로 보존한다. DB 간선과 고아 판정은 페이지 쌍 단위라 참조가 하나라도 남으면 간선이 남는다.
- 문서 연결(`source_document_ids`)은 최종 생존 근거로 센다. lint가 아닌 기록의 직접 개념 기여(개념 인용이 모두 다른 페이지로 옮겨 간 기여는 빼고, 인용 없이 이름만 나온 개념은 센다), 남은 근거 단위의 문서, 남은 하위 항목 근거 블록의 문서다. 옮긴 근거는 새 집 페이지가 센다.
- 페이지는 재생 결과 남은 유효 근거(하위 항목, 근거 단위, lint가 아닌 기록의 직접 개념 기여, 수동 기여)가 있을 때만 있다. 분리·링크 lint 기록만 남으면 재생 결과는 삭제다. lint `content_action: "delete"` 기록은 그때까지의 기록을 모두 지운다.
- 페이지 identity는 page_id다. 한 페이지의 기여가 모두 같은 slug일 필요는 없고, 개념(`concept`) 없이 하위 항목만 가진 기여도 재생한다. 개념 이름·정의는 개념을 가진 기여에서 온다.
- 본문의 `## Sub-entries` 섹션은 재생한 항목과 참조로 그리는 중첩 목록이다. 사람이 고친 본문 위에서도 다시 그리며, 항목이 없으면 섹션을 뺀다.
- `{"op": "revive", "entry_id"}`: 앞서 `remove`로 지운 항목(과 그때 함께 지운 아래 항목)을 근거째 되살린다. 지운 적 없으면 무시한다. 근거는 그 항목을 추가한 기여에서 오므로 그 기여를 되돌리면 되살릴 것이 없다.
- 본문 근거(`evidence_units`) 중 하위 항목이 인용했는데 그 항목이 이 페이지에 남지 않은 것은 본문에 넣지 않는다. 옮긴 근거는 새 집 페이지 본문에 보인다.
- 편입은 개념 판정 뒤 세부 개념을 집 페이지 기여의 `add`로 옮긴다. 근거(`evidence_units`)도 집 페이지 기여에 들어간다. 새 항목 id는 `entry:` + `sha256("{집 페이지 slug}/{세부 개념 slug}")` 앞 24자라 같은 문서를 다시 편입하면 같은 항목에 근거만 더해진다. 다른 페이지의 기존 항목과 같다고 본 항목은 그 항목 id로 집 페이지 기여에 `add`하고, 그 항목이 놓일 페이지 기여에는 `entry_reference` 링크를 둔다. 기존 항목과 같지 않은 새 항목끼리도 같은 집·같은 위 항목 아래에서 "바로 위 이름 > 이름"이 같거나 먼저 나온 형제와의 쌍 판정이 `same`이면 먼저 나온 항목의 id·이름·정의·위치로 `add`해 근거만 더한다. 집은 위 항목부터 정하므로, 다른 페이지 항목과 같다고 본 항목의 새 아래 항목은 그 항목의 집에 그 항목 아래로 들어간다. 편입은 사본(`wiki_page_entries`·`wiki_page_entry_references`)에 이번 변경을 더한 뒤 본문 목록을 사본 전체로 다시 그린다. 하위 항목으로 옮긴 개념의 연결(`link_to`)은 집 페이지에서 나가고, 집 페이지 자신을 가리키는 연결은 버린다.
- 워크스페이스 개념 목록(`list_active_concept_index`)은 개념마다 `entries`(`entry_id`·`name`·`definition`·`parent_entry_id`)를 싣는다. 같은 하위 항목 찾기의 후보다.

lint 클러스터 승격(ADR 0037, ADR 0042 4단계)은 세부 항목이 `P`개 이상인 클러스터만 승격한다. 세부 항목은 근거 줄 `claim_*: {용어} - {원문}`의 용어를 `name_key`로 묶은 것이며 클러스터 id·대표명과 같은 용어와 `ev_*` 줄은 세지 않는다. 승격 페이지의 lint 기록(`content_action: "create"`)과 핵심 개념에 병합한 lint 기록(`append_evidence`)은 세부 항목마다 `{"op": "add", "entry_id", "name": 용어, "definition": 처음 나온 줄의 원문, "parent_entry_id": null, "anchor_reference_ids": 그 용어 줄들의 블록, "evidence_claim_ids": 그 줄들의 claim id}`를 `entry_changes`에 둔다. 새 항목 id는 편입과 같은 `new_entry_id(페이지 slug, name_key(용어))`이고, 병합 대상 개념에 같은 이름의 항목이 있으면 그 id를 쓰며 개념 자신의 이름(제목·slug)인 항목은 뺀다. 사본·본문 목록은 편입처럼 사본에 더한 뒤 다시 그리고 임베딩 단위보다 먼저 쓴다. 항목 근거 블록과 승격 근거(claims)의 문서는 그 페이지의 `document_wiki_links`(`extracted_concept`)가 되고, 복구 재생도 lint 기록의 남은 항목·근거 단위 문서를 문서 연결로 센다. lint가 저장한 기록은 승격·병합·링크만 바꾼 기록까지 모두 `changed_pages`와 `ledger_contributions`(lint 기록 행, `document_id`·`linked_by_operation_id` null)에 함께 싣는다. 새 항목 id는 세부 항목을 센 것과 같은 `name_key`로 만들어 기호만 다른 이름(`C`·`C++`·`C#`)이 한 항목으로 합쳐지지 않는다. 의미 클러스터에는 관계 후보 섹션(`### Core Relation Candidates`)을 두지 않는다.

lint는 하위 항목을 다시 본다(ADR 0042 3단계, `lint_concept_entries`).
- 대상: 지난 lint(`pipeline_runs`의 `mode = 'lint'`, `status = 'succeeded'`, 결과에 `operation_id`가 있는 마지막 실행) 시작 뒤 `updated_at`이 바뀐 활성 개념 페이지와 그 lint 결과의 `deferred_entry_pages`를 기록 재생으로 읽어 모두 본다(마지막 항목이 빠져 빈 페이지도 이웃을 읽어 사라진 참조를 지운다. 분리로 만든 자식은 비었어도 다시 합치기 후보다). 그 페이지들의 기여(비활성 포함)가 더하거나 지운 `entry_reference`의 집 페이지도 본다. 참조만 바뀌면 집의 `updated_at`이 그대로라서다. 변경 표시 컬럼을 두지 않고 작업 기록으로 정한다. 판정은 이 페이지만 하고, `entry_reference`로 이어진 이웃 페이지와 자식 페이지의 부모는 함께 읽는다. 같은 lint에서 클러스터 승격이 페이지를 바꿨으면 기록이 겹치지 않게 판정 없이 모두 다음 lint로 미룬다.
- 판정: 재생한 항목과 참조로 `EntryNode`를 만들어 `decide_entry_changes`를 적용한다. 근거 수는 그 항목과 아래 항목 근거(`anchor_reference_ids`·`evidence_claim_ids`)의 고유 개수, 자식 수는 바로 아래 항목 수다. 자식 페이지는 뿌리 항목을 뺀 항목 수와, 항목 근거에 분리 뒤 자식 페이지 자체에 쌓인 근거(항목 변경 없는 편입 기록의 `evidence_units`)를 더한 수로 다시 합치기를 본다. 다시 합치기를 먼저 하고, 이번에 옮긴 항목의 아래 항목은 따로 옮기지 않는다.
- 분리·승격(새 페이지 N, 집 H, 옮긴 항목 E와 그 아래 항목): H의 lint 기록은 옮긴 항목마다 `remove`와 `{"source": "concept:H", "target": "concept:N", "relation": "entry_reference", "entry_id": E, "name", "parent_entry_id"}`(요약 줄) 추가다. N의 lint 기록은 `content_action: "create"`, 개념(제목은 E 이름, 정의는 "{H 제목}에서 나눈 하위 항목이다."), `split_from: {"page_id": H, "slug", "entry_id": E}`, `linked_operation_ids`다. 옮긴 항목을 가진 H의 편입 기록마다 같은 작업 id로 N에 기록(`pages/N/ops/{원래 작업 id}.json`)을 잇는다. 옮긴 항목을 더한(`add`) 클러스터 승격·병합 lint 기록도 같은 방식으로 잇고, 그 원장 행은 `document_id`가 null이다. 개념 없이 옮긴 항목의 `entry_changes`와 그 항목이 인용한 `evidence_units`(`related_concept_slugs`는 N)만 가진다. 다른 페이지가 옮긴 항목을 참조하면 그 페이지 lint 기록에 참조 삭제·N 대상 추가를 남긴다. H가 옮긴 항목 아래 둔 참조는 H에서 지우고 N에 더한다. 옮길 항목을 모두 정한 뒤 참조의 출발과 대상을 최종 위치로 바꾸므로, 같은 lint에서 함께 옮긴 항목끼리의 참조는 새 페이지끼리 잇는다. N의 slug는 E 이름, 이미 있으면 `{H slug}-{E 이름}`, 그다음 `-2`~`-9`를 붙이고 모두 있으면 나누지 않는다(`slug_taken`). 지운 페이지의 slug도 쓰지 않는다. 그 page_id를 다시 쓰면 옛 lint를 복원할 기록을 덮어쓴다.
- 다시 합치기(자식 C, 부모 P): P의 lint 기록은 C 항목과 뿌리 항목마다 `revive`, P → C 참조 삭제다. C의 lint 기록은 삭제 기록(`content_action: "delete"`, 재생하면 그때까지의 C 기록이 모두 지워진다)과 C가 내던 링크 삭제다. C로 오던 일반 링크(`entry_reference` 밖)는 그 링크를 낸 개념 페이지의 lint 기록 `removed_links`로 지운다. C를 가리키던 참조는 P 항목으로 대상을 바꾼다. 분리 뒤 C에만 기여한 편입 기록(`linked_operation_ids` 밖)은 항목 변경이 없어도 근거째 같은 작업 id로 P에 잇고(C에 사람이 고친 기록이 있으면 합치지 않는다, `manual_edit`), 한 lint에서 같은 작업을 P에 여러 번 이으면 한 기록으로 합친다. 그 작업이 P에도 기여했으면 페이지·작업마다 기록이 하나라 잇지 못해 합치지 않는다(`operation_on_both_pages`). C가 다른 페이지를 참조하면(손자 페이지 포함) 합치지 않는다(`has_references`). 방향 전환은 두지 않는다. 자식인지(`split_from`)와 옮길 기록은 재생처럼 마지막 삭제 기록 뒤만 본다. 합쳐 지운 뒤 같은 slug로 다시 편입된 페이지는 자식 페이지가 아니다.
- 페이지 이동(옮길 페이지 M, 대상 T): 바뀐 페이지와, 바뀐 페이지마다 저장된 벡터(`wiki_page_embeddings`의 `completed`)로 찾은 가까운 다른 페이지(활성 개념 페이지를 유사도 순으로 `REVERSE_SCAN_LIMIT`개까지 보고 옮길 수 있는 것 `PART_OF_CANDIDATE_LIMIT`개, 바뀌지 않았어도 된다) 중 분리 기록·수동 기록·분리한 자식(lint 기록이 낸 `entry_reference`)이 없고 정의가 있는 M을 통째로 다른 활성 개념 페이지 T나 T의 하위 항목 아래로 옮긴다. 후보는 페이지와 하위 항목의 임베딩 상위 `PART_OF_CANDIDATE_LIMIT`개(저장된 페이지·`sub_entry` 벡터, 바뀐 페이지와 벡터 없는 그 항목만 "이름: 정의"로 새로 임베딩), 판정은 편입 배정과 같은 `part_of`(Jev, 꺼져 있으면 lint LLM과 `prompts/concept_part_of.system.md`, 0.9 문턱)이다. M의 기록(마지막 삭제 기록 뒤의 편입 기록, 근거·항목·참조가 있는 lint 기록)마다 같은 작업 id로 T에 기록을 잇는다(`pages/T/ops/{원래 작업 id}.json`, 개념 없이 M 항목 `{"op": "add", "entry_id": new_entry_id(T slug, M slug), "name": M 제목, "definition": M 정의, "parent_entry_id": 판정한 하위 항목 또는 null, "aliases"·"tags": 그 기록의 개념 값, "anchor_reference_ids": 그 기록에서 하위 항목에 딸리지 않은 개념 인용과 근거 블록, "evidence_claim_ids": 그런 근거 단위}`, 그 기록의 `entry_changes`(맨 위 `add`·`move`의 `parent_entry_id`는 M 항목), 근거 단위 전부(`related_concept_slugs`는 T), M 하위 항목이 낸 `entry_reference`(source는 T, 편입 기록은 `links`, lint 기록은 `added_links`)). M 항목을 가리키던 다른 페이지의 참조는 그 페이지 lint 기록으로 T를 가리키고, T가 M 항목을 가리키던 참조도 자기 페이지 참조로 바꾸어 상위 위치를 보존한다. M 내부 참조의 대상과 참조 삭제 기록도 T로 옮긴다. 복수 상위 판정은 원본 집 이외의 위치에 M 항목 참조로 남긴다. T의 lint 기록은 이은 작업 id(`linked_operation_ids`)만 가진다. M의 lint 기록은 다시 합치기의 자식과 같은 삭제 기록과 M이 내던 링크 삭제이고, M으로 오던 일반 링크는 그 링크를 낸 개념 페이지 lint 기록의 `removed_links`로 지운다. M의 작업이 T에도 기여했으면 옮기지 않는다(`operation_on_both_pages`). M 항목을 참조한 페이지를 같은 lint에서 함께 옮기면 미룬다(`chained`).
- 분리 관계 재판정(ADR 0042 결정 6): 분리한 집 H의 `concept_related_to`(H에서 나가는 것과 다른 개념 페이지 A에서 H로 오는 것)마다 A가 새 페이지 N과 관련인지 H와 관련인지 Jev(`judge_related`, 같음·관련 판정과 같은 기준, related 0.9 문턱)로 묻는다. N 쪽이면 링크를 N으로 옮긴다. H가 내던 링크는 그 링크를 낸 H의 기록을 원래 작업 id로 N에 잇고(`links`에 N → A, `linked_by_operation_id`는 이 lint), A가 내던 링크는 A의 lint 기록 `added_links`에 `requires_operation_id`(원래 링크를 낸 작업)와 함께 둔다. 재생은 `requires_operation_id`의 기록이 그 페이지 재생에 있을 때만 그 링크를 잇는다. H 쪽이 아니면 원래 링크는 그 링크를 낸 페이지의 lint 기록 `removed_links`로 지운다. 양쪽이면 원래 링크를 남기고 N 쪽만 더한다. 판정할 수 없으면(정의 없음·Jev 없음) 옮기지 않는다.
- 원문 출처 정리: 문서를 지워도 개념 페이지는 바로 지우지 않고 lint가 정리한다. lint는 바뀐 페이지와 상관없이 활성 개념 페이지 전체를 본다. 출처는 재생 결과의 문서(`source_document_ids`) 중 소스 페이지가 활성이고 tombstone이 없는 문서다. 출처가 없으면 수동 기여가 있어도 삭제 기록(`content_action: "delete"`, `action: "prune_unsourced"`)을 남기고 지운다. 그 페이지로 오던 일반 링크와 참조는 그 링크를 낸 페이지 lint 기록의 `removed_links`로 지운다. 출처가 있는데 소스 → 개념 링크가 없으면 문서 연결을 다시 쓰고 링크를 맞춘다(`source_link_repairs`, 파생 상태라 lint 기록은 남기지 않는다). 소스 → 개념 링크가 있고 기여가 모두 켜진 페이지는 재생하지 않는다. 기여 행이 없어도 링크가 있으면 출처가 있는 것으로 보고 남긴다. 기여 행도 링크도 없으면 본문이 인용한 문서로 판정해, 살아 있는 문서가 있으면 잇고 없으면 지운다. 기록을 재생할 수 없는 페이지와 지난 lint 기록이 원장에 아직 오르지 않은 페이지는 지우지 않는다. 같은 lint에 승격이 있으면 하위 항목 판정은 다음 lint로 미루지만 출처 정리는 그대로 한다. 이번에 승격한 페이지는 소스 → 개념 링크가 없고 원문도 찾을 수 없으면 승격 기록을 삭제 기록으로 바꿔 지운다. lint를 복원해도 기여가 모두 꺼진 페이지는 돌아오지 않으며, 지우기 직전 본문은 lint 기록의 `.md`와 document-svc 버전에 남는다. 문서를 복구해 다시 편입하면 페이지가 다시 생긴다.
- 사라진 참조: 복원은 가리키던 항목이 최종 상태에 없는 참조를 같은 복원에서 참조 사본·본문 목록·간선에서 뺀다(참조하는 다른 페이지는 활성 기록으로 다시 그린다). lint는 가리키던 항목이 없어졌거나 집 페이지가 지워진 `entry_reference`를 참조하는 페이지 lint 기록의 `removed_links`로 지운다. 그 기록의 재생으로 참조 사본·본문 목록·간선이 함께 정리된다. 집 페이지가 지워졌는지는 바뀐 페이지 기여가 가리킨 집 중 살아 있는 페이지가 없는 것으로 본다.
- 원장: 결과의 `ledger_contributions`(`page_id`·`operation_id`·`document_id`·`contribution_key`·`linked_by_operation_id`)는 document-svc가 기여 원장에 더할 행이다. 이 lint가 저장한 기록은 모두 행이며 `document_id`·`linked_by_operation_id`가 null, 이은 기록은 원래 작업 id와 문서이고 `linked_by_operation_id`가 이은 lint다(기여 JSON에도 같은 표시). 행은 lint 기록, 이은 기록 순서로 더한다(재생 순서). 원장 행은 일괄 비활성화하거나 다시 켜지 않는다. 합친 자식의 기존 기여도 활성으로 남고, 자식이 없어지는 것은 삭제 기록을 재생한 결과다. lint 복원은 `operation_id`나 `linked_by_operation_id`가 대상 lint인 행만 빼고 그 페이지를 재조립한다. 다시 합치기 복원은 그 lint 기록이 지운 링크 중 남은 기록이 아직 잇는 것만 되살린다.
- 판정 순서: 다시 합치기, 그다음 분리·승격을 위 항목부터 한다. 이미 옮긴 항목의 아래 항목은 옮기지 않는다(`ancestor_moved`). 이번 lint에서 자식을 합쳐 받은 부모의 분리·승격은 합친 뒤 항목으로 하도록 다음 lint로 미룬다(`parent_merged`, `deferred_entry_pages`). 페이지 이동은 그 뒤에 모두 정한다. 페이지마다 확률이 가장 높은 상위 하나만 보고, M이나 상위 페이지가 이번 lint의 다른 판정에 걸리면(`page_busy`), 이번에 옮긴 페이지를 상위로 두거나 이번에 상위가 된 페이지를 옮기면(`chained`) 다음 lint로 미룬다.
- 현재 상태: 바뀐 페이지는 기록 재생 결과로 본문·항목 사본·항목 참조 사본(`wiki_page_entry_references`)·문서 연결·임베딩 단위를 다시 쓰고(쓰지 않게 된 벡터는 모든 페이지 단위를 쓴 뒤 한 번에 지워, 옮긴 항목의 벡터를 그대로 쓴다), `wiki_page_links`는 재생한 링크의 페이지 쌍 차이만 반영한다.

Concept 페이지 frontmatter의 `tags`는 추출 단계가 원문 근거로 붙인 분야·분류 태그(최대 3개, 제목·별칭과 중복 제외)를 `sources`처럼 쉼표로 이어 쓴 값이며, 없으면 빈 값이다. 기존 개념 목록은 이 값을 `tags` 목록으로 노출한다. 태그는 개념 후보 사전 필터링용 색인이며, 같은 개념인지 판정하는 근거로 쓰지 않는다. lint 승격 페이지는 태그 없이 만들어진다.

LLM provider/model은 workspace 설정 또는 chat/request에서 snapshot되어 command와 실행에 전달된다. API key는 DB·Kafka payload·log에 저장하지 않고 ai-svc secret env에서만 읽으며, 기존 AI 작업 로그 조회/결과 경로에는 LLM 설정 컬럼이 없다.

문서 편집 저장은 document-svc가 소유한 `core_db` PostgreSQL transaction에서 본문·편집 상태·write receipt·content version·asset/reference·Agent 적용 감사·`document_edit_outbox`를 함께 commit 또는 rollback한다. V39는 `document_edit_states`와 `document_content_versions`가 모두 빈 상태에서 시작하는 fresh cutover이며, 기존 Mongo 편집 데이터와 두 PostgreSQL table의 폐기는 대상별 승인을 전제로 한다. 기존 편집 데이터 import, fallback, dual-write를 사용하지 않는다. 결정 근거: [adr/0016](https://github.com/FruitionKR/Fruition-document/blob/main/docs/adr/0016-consolidate-document-body-into-postgres.md). S3/MinIO object upload는 transaction 밖이므로 실패·무변경 저장 시 업로드 호출자가 object를 정리한다. outbox publisher는 `created_at,event_id` 순으로 처리하고 첫 실패에서 cycle을 중단하며 현재 1 replica 전제를 둔다.

음성 API는 새 테이블을 만들지 않는다. 음성 bytes·실시간 미확정 전사는 요청/연결 안에서만
처리한다. 확정 전사와 원본 녹음의 영구 저장은 호출 서비스가 소유하며 AI는 회의록 초안을
반환한다. 연결 종료 전에 `completed` 구간을 저장하는 계약은 [음성 API](api/speech.md)를 따른다.

## AI 모델 사용량 원장 (`ai_model_usage`, AI DB 소유)

호출 UUID를 키로 실행·workspace·사용자·작업 종류, provider, 요청 모델과 응답 모델, 호출 상태(`started`·`succeeded`·`failed`·`abandoned`·`cancelled`), 입력·출력·캐시·reasoning 토큰, 음성의 오디오 길이(`audio_seconds`)와 TTS 입력 문자 수(`input_characters`), 시작·종료 시각과 호출 시간을 저장한다. 귀속 값이 빠진 호출은 `unattributed`로 남고, 1시간 넘게 `started`인 행은 조회 직전에 `abandoned`로 닫힌다. 첫 문답의 채팅 제목 호출(`kind=session_title`, run_id는 그 문답과 같다)은 답변을 늦추지 않으려고 결과 발행 뒤에 시작하지만, document-svc가 수집 때 놓치지 않도록 행만 발행 전에 `started`로 연다. 모델을 부르지 않고 끝나면 그 행을 지운다. command의 `session_title_needed`가 `false`인 세션은 제목을 만들지 않으므로 행도 열지 않는다. 프롬프트·응답 본문·API 키는 저장하지 않는다. 미수신 사용량은 NULL이며 알려진 토큰 합계와 미확인 호출 수를 분리한다. 작업 취소 보상에 포함하지 않아 이미 사용한 토큰을 보존한다. 사용자·워크스페이스 [AI 데이터 파기](api/purge.md) 때도 정산용으로 남기며 보관 기간은 법률 검토 뒤 정한다. 파기한 범위의 식별자는 `ai_purged_scopes`에 남겨 재전달된 작업을 거절한다. 백엔드는 AI DB에 직접 접속하지 않고 내부 사용량 API를 조회한다.
