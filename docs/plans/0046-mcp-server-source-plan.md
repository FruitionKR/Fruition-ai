# 0030. 사용자 모델이 작업하는 MCP 서버를 document-svc에 둔다

> 번호 메모: Fruition-document(0029 credit-preauthorization-threshold, 0030 wiki-permission-enforcement)와 Fruition-ai(0029 ai-data-purge-contract, 0030 sync-http-usage-attribution-header) 모두 0029·0030을 이미 쓴다. 넣을 저장소가 정해지면 이 문서와 BYOK 문서([0029](0029-byok-user-llm-key.md))의 번호를 다시 매긴다.

## Status

Proposed

## Context

Claude 원격 커넥터를 우선 대상으로, MCP 클라이언트를 쓰는 사용자가 자기 구독 모델로 우리 위키와 문서를 다루게 하려고 한다. Cursor 등 추가 클라이언트는 인증 호환성 검증을 통과한 뒤 지원 목록에 넣는다. 추론은 사용자 모델이 하고, 우리는 데이터 조회·검증·저장을 맡으면서 플랫폼 수수료를 받는다.

- 이 제품은 클라이언트가 시작하는 tool 호출만 쓴다. 웹 버튼으로 시작한 작업을 사용자 모델에 보내는 경로는 제공하지 않는다. 웹 경로에서 사용자 계정으로 LLM을 쓰는 것은 [0029](0029-byok-user-llm-key.md)(BYOK)가 맡는다.
- 서버가 클라이언트 모델에 추론을 요청하는 sampling은 MCP 2026-07-28 사양에서 deprecated 됐다. elicitation 같은 서버 발신 요청도 core에서 제거됐다.
- 별도 API Gateway는 없다(Fruition-flatform `docs/architecture.md`). document-svc가 access가 발급한 JWT를 직접 검증한다. access의 JWT는 RSA 서명에 `iss`·`aud`(`fruition-api` 고정)를 필수로 검증하며, 우리 웹앱과 데스크톱 앱(PKCE 딥링크)에만 발급된다. 외부 클라이언트용 인가 서버 기능(메타데이터, 동의 화면, 클라이언트 등록)은 없다.
- ai-svc는 외부에 노출되지 않는다. `pipeline/api.py`는 내부 API에 `X-Internal-Token` 인증 미들웨어와 의존성을 적용하고, Agent run·Skill API에는 별도의 `X-Agent-Service-Token` 의존성을 적용한다. 서비스 호출자 인증과 네트워크 격리가 경계이며, 이 토큰들은 최종 사용자 신원을 증명하지 않는다. 요청의 `workspace_id`·`user_id`에 대한 사용자 인증과 workspace 인가는 호출 서비스(document-svc·access-svc)의 책임이다.
- 권한은 workspace 역할(OWNER·MEMBER)과 권한 항목(`wiki.ingest`·`wiki.lint`·`skill.author`·`wiki.restore`·`document.convert`)이다(ai ADR 0033, document ADR 0030). 문서·폴더 권한은 `edit|view`뿐이라 **멤버는 workspace의 모든 문서를 읽을 수 있다**.
- 위키는 workspace 전원이 보는 공유 자산이다. 위키 ingest는 `wiki.ingest` 권한이 있는 멤버의 수동 편입 외에도, workspace의 `auto_ingest_on_upload` 설정과 요청자의 권한에 따라 Markdown·txt 업로드 뒤 또는 PDF 변환 뒤 자동으로 시작될 수 있다(`DocumentService.autoIngestAfterCommit`, `ingestConvertedParts`; 스킬 참고 문서·가져오기 등 기존 제외 조건 유지). 편집 이벤트(`document.edit.event`)는 stale 상태만 기록하며, ingest 직후에는 post_ingest lint(`app/workers/ingest_worker.py`의 `_dispatch_post_ingest`)가 이어진다.
- concept 페이지는 작업별 기여 JSON(개념·근거·링크)으로 다시 조립된다(`rebuild_concept_page`, ai ADR 0031). 기여 원장(`wiki_page_contributions`)으로 작업 단위 복구가 된다.
- Agent 계획은 지금 worker의 LLM 플래너만 만든다(`agent_worker.py`의 `_plan_run` → `save_plan`). 승인 뒤 실행은 checkpoint가 없으면 `start_execution`으로 바로 들어간다.
- Claude의 원격 커넥터(claude.ai·Desktop·모바일·Claude Code 공통)는 OAuth 2.0을 쓴다. 고정 토큰(`static_headers`)은 조직 Owner가 한 번 입력해 조직 전원이 같은 값을 쓰는 베타 기능이라 사용자를 식별할 수 없다. Claude가 따르는 사양은 2025-11-25다.
- 공식 MCP Java SDK의 정식판 `v2.1.0`은 2025-11-25 사양까지 지원한다. 2026-07-28 stateless 서버는 `v2.2.0-M1`(2026-10-16, 마일스톤)에만 있다.

## Decision

### 배치

- MCP 엔드포인트는 **document-svc에 Java(공식 MCP Java SDK)로 둔다.** document-svc가 resource server로서 MCP 토큰을 검증한다.
- **access가 인가 서버를 맡는다.** 기존 로그인(이메일·소셜)은 그대로 두고, 그 위에 MCP 토큰 발급·동의 화면·클라이언트 식별 층을 얹는다. Spring Authorization Server 도입을 우선 검토한다. MCP 서버는 토큰을 검증만 하고 발급하지 않는다. Sentry는 기존 Sentry OAuth 앞에 별도의 MCP 인가 층을 두므로 우리와 배치가 다르다. 참고하는 원칙은 MCP 토큰과 기존 API 토큰의 분리다.
- document-svc가 tool 정의와 인가를 맡는다. 문서 tool은 document-svc 내부에서 처리하고, 위키·편입·lint tool은 ai-svc 내부 HTTP를 호출한다.
- ai-svc는 MCP 프로토콜을 처리하지 않는다. document-svc가 호출할 기존 내부 API를 재사용하고 필요한 API만 추가한다. 새 Agent run API는 기존 `X-Agent-Service-Token` 인증 경로에, 조회·위키 API는 `include_internal_router`의 `X-Internal-Token` 인증 경로에 등록한다.
- MCP 사양은 **2025-11-25로 시작한다**(SDK `v2.1.x`). 주요 클라이언트가 2026-07-28로 옮겨 가고 Java SDK 2.2.0 정식판이 나오면 함께 옮긴다. 옮기기 쉽게 tool 사이의 상태는 처음부터 세션이 아니라 명시적 handle(`run_id`)로 다룬다.

### 인증

- **OAuth만 지원한다.** Claude 원격 연결 호환성과 동의·회수 경험을 하나로 통일하기 위해서다. 사용자별 PAT도 사용자를 식별할 수 있지만 이번 범위에는 넣지 않는다. Claude의 조직 공용 고정 헤더는 개인별 사용자 식별에 맞지 않으므로 지원하지 않는다.
- Claude의 요구사항을 따른다:
  - 토큰 없는 MCP 엔드포인트 요청은 `401`과 `WWW-Authenticate: Bearer resource_metadata=...`로 답한다. protected resource metadata의 `resource`는 MCP URL과 정확히 같고, `authorization_servers`의 첫 항목이 access다. protected resource metadata와 access의 인가 서버 metadata는 인증 전에 조회할 수 있도록 정확한 경로를 공개한다. 기존 웹 JWT 필터가 discovery나 MCP 전용 토큰 검증을 먼저 막지 않도록 보안 필터 적용 범위를 분리한다.
  - access는 RFC 8414 메타데이터를 내고 `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported`의 `none`, `code_challenge_methods_supported: ["S256"]`을 광고한다. S256 PKCE만 받는다.
  - redirect는 `https://claude.ai/api/mcp/auth_callback`과 Claude Code의 loopback(`localhost`·`127.0.0.1`, 포트 무시)을 받는다. 동의 화면에 redirect 호스트를 표시한다.
  - refresh token을 회전하고, 무효한 refresh에는 `invalid_grant`로 답한다. 회전 전후 토큰의 계열 관계를 보관하며, 이미 사용된 토큰의 재사용을 탐지하면 해당 계열의 현재 활성 refresh token도 폐기한다(RFC 9700 §4.14.2). 기존 `AuthService.refresh`의 옛 토큰 거절만으로는 이 계약을 충족하지 않는다. 회전·재사용 탐지·폐기는 동시 요청에서도 원자적으로 처리하고, 오류 응답 때문에 폐기가 롤백되지 않게 한다. discovery·token 엔드포인트는 10초 안에 응답한다.
- **인가 코드는 동의한 문맥에 묶는다.** 짧은 수명의 일회용 코드에 client ID·인가 요청에서 검증한 redirect URI·MCP resource·PKCE challenge 및 사용자·workspace·동의 scope·grant를 결합한다. 인가·토큰 요청의 `resource`를 허용된 MCP URI와 대조하고, 코드 교환 시 client·redirect·resource·verifier를 검증한다. loopback의 포트 예외는 클라이언트 등록값과 인가 요청을 비교할 때만 적용하며, 코드에는 실제 요청의 포트를 포함한 redirect URI를 고정한다. 사용자·workspace·scope는 교환 요청으로 바꿀 수 없고, 동시 교환에서도 한 번만 토큰을 발급한다. 기존 `OAuthExchangeCodeStore`는 사용자와 선택적 PKCE challenge만 저장하는 로그인 교환 코드이므로 MCP 인가 코드로 그대로 사용하지 않는다. 인가 서버 라이브러리를 도입하면 해당 표준 기능을 재사용하고 서비스의 grant 문맥만 연결한다.
- **클라이언트는 허용 목록으로만 받는다.** CIMD URL(예: Claude Code `https://claude.ai/oauth/claude-code-client-metadata`)을 목록에 둔다. Dynamic Client Registration은 열지 않는다. 목록에 없는 클라이언트는 CIMD 조회와 동의 화면 전에 거절한다. HTTPS CIMD URL 전체를 정확히 비교하고 redirect는 따라가지 않는다. 조회 연결은 사설·loopback·link-local/메타데이터 주소를 차단하며 응답 크기·시간 상한을 둔다. 응답의 `client_id`는 요청 URL과 일치해야 하며 redirect URI는 해당 클라이언트의 등록값과 대조한다.
- 허용 목록은 클라이언트 등록 정보를 제한하며 설치된 앱의 진위를 증명하지 않는다. 특히 `none` 인증과 loopback에서는 다른 로컬 앱도 정상 CIMD 주소로 자신이 시작한 PKCE 흐름의 동의를 요청할 수 있다. loopback 지원은 유지하되 동의 화면에 앱 신원 미검증 경고와 redirect 호스트를 표시하고, 관리자 허용 화면에도 이 한계를 알린다. 등록된 클라이언트 이름을 앱 진위 검증 표시로 쓰지 않는다.
- 출시 전 클라이언트별 CIMD/client ID, 정확한 redirect URI(등록된 loopback의 포트 예외만 허용), discovery, refresh, scope 추가 동의(step-up)를 실제 연결로 검증한다. step-up을 지원하지 않으면 재연결로 명시적 동의를 받으며 scope를 자동 확대하지 않는다. 허용 목록 등록만으로 호환성을 보장하지 않는다.

### grant와 연결 회수

- 연결 하나에 workspace 하나를 묶는다. OAuth 동의 화면에서 workspace를 선택하고, access가 멤버 여부와 관리자 허용을 확인해 grant에 user·workspace·client·scope를 저장한다. 기존 웹 JWT에는 workspace claim이 없으므로 그대로 MCP 토큰으로 재사용하지 않는다.
- MCP 토큰에 `grant_id`를 넣고, 매 호출 토큰 검증과 별도로 access의 grant 활성 상태 및 workspace MCP 허용 상태를 확인한다. user·workspace·client는 검증된 토큰과 grant의 일치하는 문맥에서만 결정한다. 유효 scope는 토큰·현재 grant·관리자 허용 범위의 교집합이다. 확인에 실패하면 허용하지 않는다. 폐기 반영을 늦추는 양성 캐시는 두지 않는다.
- 멤버십·권한의 정책은 기존 `requireMember`·`requirePermission`과 동일하게 유지하되, MCP의 판정 근거로 `authz:role:v2` 캐시를 사용하지 않는다. 기존 캐시 무효화는 실패 시 이전 권한이 최대 300초 남는 계약이다. 매 호출 access의 grant/관리자 정책 확인에 현재 멤버십·역할·필요 권한의 원본 저장소 판정을 포함하고, 웹 승인 및 각 변경 직전에도 다시 확인한다. 원본 판정은 기존 `InternalAuthzController.role`의 `findActiveMember`·`effectivePermissions` 로직을 재사용하고 grant·관리자 정책과 결합한다. 조회 실패 시 캐시로 대체하지 않고 차단한다. document의 문서·폴더 정책도 이 최신 역할을 사용하며, OWNER 예외 등을 판단할 때 이전 캐시 값을 다시 읽지 않는다. 연결 해제·관리자 MCP 비활성화에는 이와 별도로 grant/관리자 정책 검증이 필요하다. 토큰 서명·만료 검사나 refresh 폐기만으로 이미 발급한 access token의 즉시 회수가 되지는 않는다.
- 모든 MCP 제안·draft·run에 원래 grant와 client를 기록한다. 연결 해제 또는 강제 회수된 grant의 미승인 제안·draft는 승인 불가로 만들고 정리한다. 관리자 MCP 비활성화 시에도 미승인 제안·draft를 무효화한다. 재연결이나 관리자 재활성화로 과거 제안이 되살아나지 않는다. 무효화 처리가 지연돼도 웹 승인 API가 grant와 정책을 다시 검사해 차단한다.
- **사용자 본인의 연결 해제:** 새 MCP 호출·제안·승인은 막지만, 해제 전에 사람이 웹에서 승인한 실행은 계속한다. 실행의 근거는 고정된 웹 승인 기록이며 현재 멤버십·권한과 관리자 차단 상태는 매 변경마다 확인한다. 이 실행 판정은 사용자 해제로 비활성화된 grant 자체를 거절 사유로 삼지 않고, 관리자·보안 회수와 구분한다. 연결 해제 화면에 이 차이를 표시하고 기존 작업 취소로 연결하되, 이 취소는 이미 수행한 변경의 역순 복구를 요청한다는 점을 알린다.
- **refresh 재사용 탐지에 따른 보안 회수:** refresh 계열 폐기에 더해 해당 MCP grant를 보안 사유로 강제 회수한다. 이는 이미 발급한 access token도 차단하기 위한 서비스 정책이며 RFC의 refresh 폐기 요구와 구분한다. 아래 관리자 강제 회수와 같은 미승인 제안 무효화·다음 변경 경계 중단 규칙을 적용한다. 재연결은 새 grant로 처리한다. 계열을 식별할 수 없는 임의의 무효 토큰으로 다른 grant를 회수하지 않는다. 정상 클라이언트의 동시 갱신이나 응답 유실 후 옛 토큰 재시도도 재사용으로 처리하므로 재연결이 필요할 수 있다.
- **관리자 MCP 비활성화·관리자 강제 회수:** 이미 승인된 실행도 다음 변경 작업 경계에서 중단한다. 실행 중인 단일 작업까지 소급 취소할 수 있다는 보장은 하지 않는다. 각 변경 직전에 실행 차단 상태를 검사하며, 상태 확인 실패 시 새 변경을 실행하지 않는다. 정책 변경과 진행 중 커밋 사이에 분산 원자성을 보장하지 않는다.
- 관리자 중단에는 롤백 없는 종료 상태 `halted`를 추가한다. 기존 `cancel`은 `_request_rollback`을 호출하므로 관리자 중단에 재사용하지 않는다. worker 종료 상태·실행 인가·상태 API·UI·정산을 함께 갱신하고, `halted`에서도 사람이 기존 복구를 명시적으로 요청할 수 있게 한다. 기존 사용자 cancel의 역순 복구 동작은 유지한다.
- 관리자 차단 시 access에 workspace 차단 세대와 grant 강제 회수 사유를 영속화한다. 제안·승인 기록의 세대와 비교하므로 짧은 off→on 사이를 worker가 놓쳐도 이전 실행은 재개되지 않는다. 무효화된 제안·draft도 다시 승인할 수 없다. 재활성화 후 실행하려면 새 제안과 승인이 필요하다.
- 멤버 제거·권한 회수는 기존 실행 시 권한 검사로 차단한다. 회수만으로 이미 완료된 변경을 자동 롤백하지 않는다. 성공 결과·취소 상태를 이력에 남기고, 사람이 웹에서 기존 복구 권한(`wiki.restore` 등)에 따라 되돌린다. MCP 연결이 꺼져 있어도 적법한 웹 이력 조회·복구를 막지 않는다.

### 조회 전용 내부 API

- `search_wiki`는 기존 검색기와 저장소만 호출하는 ai-svc 내부 API를 쓴다. 답변 생성기·평가기·대화 요약기가 묶인 `build_answer_query_use_case`나 `/agent/turn`을 호출하지 않는다. 문서 검색·조회는 document-svc의 기존 권한 판정과 저장소를 재사용한다.
- `get_wiki_page`는 기존 `GET /wiki/pages/{page_id}?workspace_id=...`를 재사용하고, 필요한 버전/해시·응답 제한만 보완한다. 일괄 메타데이터 조회가 필요하면 기존 `POST /wiki/pages/lookup`을 쓰되, 기존 계약에서 선택값인 `workspace_id`를 MCP 경로에서는 검증된 grant로부터 반드시 채운다. 기존 내부 응답을 그대로 외부에 노출하지 않고 MCP 응답 계약에 맞춘다.
- 검색 결과는 문서·페이지 ID, 버전 또는 내용 해시, 근거 블록 참조, 길이를 제한한 snippet, 다음 페이지 cursor를 반환한다. 본문은 별도 조회 tool로 가져온다. 검색·본문 응답 모두 개수·크기 상한을 둔다.
- cursor도 권한이 아니다. 사용자·workspace·검색 조건에 묶고 다음 페이지마다 인가한다. 원문과 snippet은 신뢰할 수 없는 데이터로 표시한다.
- 생성형 LLM을 호출하지 않아도 검색 임베딩·DB·네트워크 비용은 발생한다. 검색 임베딩 비용은 답변 생성 비용과 구분해 계측하고 읽기 한도에 반영한다.
- 검색 요청에서는 질문만 임베딩하고, 저장 벡터가 없는 후보 본문은 즉석 임베딩하지 않는다. 기존 `StoredWikiPageEmbeddingSearch.without_live_embedding()`을 재사용한다. 응답 크기·호출 횟수 제한과 별도로 DB 후보 조회 단계부터 후보 수·총 텍스트량·처리 시간에 상한을 두며, workspace 전체를 읽은 뒤 응답만 잘라 제한한 것으로 취급하지 않는다.

### Agent 역할 분담

- MCP 경로에서는 클라이언트 모델이 Agent다. 의도 분류(라우터·Jev), 계획 수립, Query 답변 작성, 편집안 생성을 클라이언트 모델이 맡는다.
- 서버는 Query와 Agent를 구분하지 않고 하나의 tool 집합을 제공한다.
  - 읽기: `search_wiki`, `get_wiki_page`, `find_documents`, `get_document`
  - 쓰기 제안: `propose_document_edit`, `propose_plan`(`create_document`·`create_folder`·`rename_*`·`move_*` 등 `PlanToolName` 범위, 1~20개 작업)
  - 위키: ingest tool, `submit_lint_changes`
- Skill은 MCP로 노출하지 않는다(보안 T6).

### 문서 편집·변경

- 쓰기 tool은 즉시 실행하지 않는다. 기존 Agent run 승인·실행 경로에 올린다.
  1. `propose_document_edit(document_id, base_version, target, instruction, replacement_markdown)` 또는 `propose_plan`을 받는다. `instruction`은 클라이언트가 전달한 요청 문장이며 신뢰할 수 없는 입력이다. 실제 사용자 의도의 증거로 취급하지 않는다. `validate_markdown_output`은 요청 문장 자체의 의미를 검증하지 않으며, 편집 목표·작업 유형 등 구조화된 계약과 출력 형식을 검사한다. 최종 변경 의도는 웹 미리보기 승인으로 확인한다.
  2. document-svc가 멤버 여부와 대상 문서·폴더·이동 목적지의 필요한 권한을 기존 정책으로 검사한다. 문서 편집은 `DocumentAccessPolicy.requireEdit`을 재사용하며 소유자·OWNER 예외도 동일하게 적용한다.
  3. ai-svc의 **새 내부 API**가 run과 계획을 LLM 플래너 없이 직접 만든다. 이 API는 웹 경로와 같은 편집 계약(`validate_markdown_output`), source range, `ai_markdown_sanitizer`의 `keep_urls`, 대상 폴더 범위, 계획 구조(`build_agent_plan`) 검증·정규화를 거친다. 이름·내용 중복 검토(`review_duplicate_names`·`review_content_duplicates`)는 제출 거절 조건이 아니라 기존 웹 경로처럼 경고를 붙이고 해당 작업과 의존 작업을 기본 선택에서 제외하는 절차다. 필수 검증을 통과하면 artifact를 등록하고(`POST /internal/agent/runs/artifacts/register`), 중복 경고를 반영한 `awaiting_approval` 계획을 저장한다.
  4. 클라이언트에는 run_id와 diff 확인 링크를 돌려준다.
  5. 사용자가 승인하면 plan version·`operation_hash` 검증, `base_version` 충돌 검사, 실행, 롤백을 웹 경로와 같은 코드로 처리한다. 실행 시점에도 편집 권한을 다시 검사한다.
- **플래너의 결정적 검증을 공통화한다.** `build_agent_plan`은 작업 수·순서·의존성 등 형식만 검증한다. `chat_completions_plan_generator.py`의 `_validate_plan_against_hierarchy`, `_validate_artifact_arguments`, `_validate_artifact_reference`와 폴더 범위 처리(`_place_creates_in_target_folder`, `_scope_moves_to_target_folder`)를 공통 경로로 옮겨 웹 플래너와 MCP 제출이 모두 호출한다. 정규화한 최종 계획을 검증·해시 계산·미리보기 대상으로 삼는다. `save_plan`이나 artifact 등록 성공을 검증 완료로 취급하지 않는다.
- **승인은 웹앱에서만 받는다.** MCP에는 승인 tool을 두지 않는다. 클라이언트 모델이 스스로 승인하거나 문서에 숨은 지시로 승인이 유도되는 것을 막고, 사람이 diff를 반드시 보게 하기 위해서다.
- **MCP 제안은 사용자 자동 승인 설정의 대상에서 제외한다.** 서버가 생성 시 영속화한 출처로 구분하며 클라이언트 입력으로 바꿀 수 없다. `AgentTurnService.getRun()`의 조회 시 자동 승인과 plan-ready 알림 경로 모두 MCP run을 승인 대기로 유지한다. document와 ai의 승인 API도 MCP run에 대한 자동 승인 요청을 거부하고, 웹에서 명시적으로 제출된 사용자 승인만 수락한다. ingest·lint draft에도 같은 원칙을 적용한다.
- 승인 화면에는 MCP 제안임을 표시하고 등록된 클라이언트 이름, 선택한 작업 범위, 수수료와 부분 성공 과금 규칙을 보여 준다. 클라이언트가 보내온 임의 표시 이름을 신뢰하지 않는다. 승인에는 grant·plan version·operation hash·선택 operation ID·단가·계획당 상한·가격 버전을 묶는다.
- 미리보기는 기존 `MarkdownEditPreview`·`MarkdownViewer`의 텍스트 diff, `skipHtml`, `inert-external`, 관리 이미지 정책과 화면 CSP(`frame-ancestors 'none'`)를 재사용한다. 새 ingest·lint 미리보기의 제목·인용도 텍스트로 처리한다. 화면을 열기만 해도 스크립트가 실행되거나 외부 이미지가 요청되지 않아야 한다. OAuth 동의 화면에도 클릭재킹 방어를 적용하고, 쿠키 기반 동의 제출에는 CSRF 방어를 적용한다. 기존 Bearer 기반 승인 API에는 쿠키 인증을 암묵적으로 추가하지 않는다.
- **MCP run은 웹앱의 수정 요청(revise)을 받지 않는다.** revise는 서버 LLM 플래너로 돌아가기 때문이다. 웹앱에서는 제안 승인·거절과 기존 실행 취소·복구를 제공하고, 계획 수정은 MCP 대화에서 새 제안으로 한다.
- **MCP 실행의 호출 예산 소진은 추가 확인 대기로 남기지 않는다.** 기존 40회 한도를 유지한다. worker의 `react_tool_budget_insufficient`는 웹 경로에서 `clarification_required`로 전환하지만, MCP에서는 미착수 작업을 `skipped`와 한도 소진 사유로 기록하고 기존 검증 → `finish_run_from_operations` 경로로 종료한다(`failed`·`partial_failed`·`conflicted` 등 기존 집계 규칙). 이미 시도한 작업은 미착수로 덮어쓰지 않으며, 확인되지 않은 실행 결과를 별도 사유·대사 대상으로 보존한다. 완료된 변경은 자동 롤백하지 않는다. 새 예산 컬럼이나 종료 상태를 추가하지 않고 기존 `authorize_tool_execute`의 run·operation 상태 검사와 worker의 조건부 상태 갱신을 재사용한다. 이미 인가를 통과한 요청의 늦은 커밋까지 막았다고 보장하지 않으며 실행 영수증으로 대사한다. 최대 20개 작업의 정상 진행에서는 단계 한도에 도달하지 않아야 하므로, `react_step_limit_exceeded`는 정상 사용자 질문이 아닌 진행 불능 오류로 처리한다. 관리자 차단용 `halted`와 구분하고 웹 경로의 기존 추가 확인 동작은 유지한다.
- 편집 품질 평가 LLM([0011](0011-user-approved-markdown-edits.md))은 MCP 경로에서 실행하지 않는다. 서버 LLM 비용이 생기기 때문이다. 사용자의 diff 확인과 승인이 안전장치다.

### 경로와 저장

- MCP로 만든 결과(위키 페이지, 근거 연결, 작업 이력)는 웹 경로와 같은 저장소·테이블에 저장한다. 클라이언트는 결과물을 만들어 제출할 뿐이다.
- 클라이언트가 제출한 결과는 신뢰할 수 없는 입력으로 다룬다. 실패하면 이유를 돌려주고 반영하지 않는다.

### MCP ingest

- tool 흐름: `start_ingest` → `get_window` / `submit_window` 반복 → `finalize_ingest`. 끊긴 run은 `resume_ingest`로 다음 window부터 이어 간다.
- `start_ingest`에서 원문의 버전·내용 해시와 블록 스냅샷을 고정한다. `get_window`와 `submit_window`는 같은 스냅샷만 사용한다. run 중 최신 원문으로 조용히 교체하지 않는다.
- 미리보기 승인은 `draft_version`·`draft_hash`에 묶는다. 승인 후 draft는 수정할 수 없다. 승인 시와 실제 반영 직전에 원문 버전·해시를 검사하며 불일치하면 거절하고 새 run으로 다시 제안한다. 해시는 본문뿐 아니라 반영할 기여·대상·근거 스냅샷과 아래 전체 변경 집합 및 관련 ai_db 공개 상태의 지문을 포함한다. 공개 상태의 지문은 본문 참조·버전과 항목·링크·참조를 포함하며 기존 위키 상태 전체를 별도 복제하지 않는다.
- 시작할 때 document-svc가 `wiki.ingest` 권한을 검사한다(`requirePermission`). `submit_lint_changes`는 `wiki.lint`를 검사한다.
- **클라이언트의 window 처리 실행은 Kafka worker에 맡기지 않는다.** run과 window 진행 상태를 ai_db에 바로 저장한다. 결과·정산 이벤트의 outbox 전달과 기존 편집 이벤트 소비는 별개다.
- 문서당 활성 run은 하나다. 수동 편입·업로드 후 자동 편입·변환 후 자동 편입과 MCP run이 같은 문서를 동시에 편입하지 않도록 공통으로 잠근다. 진행이 없는 run은 만료시키고 잠금과 draft를 정리한다.
- task journal(`postgres_task_journal`)에 등록하고 MCP draft·실행 상태와 취소·복구 계약을 연결해 웹앱의 상태 표시·취소·역순 복구(`/internal/ai/tasks/...`)가 동작하게 한다. journal 등록만으로 새 경로의 취소·복구가 완성되는 것은 아니다.
- **공유 위키 인젝션 방어.** 원문 문서에 심긴 지시는 웹 경로와 같은 위험이다. MCP에서 새로 생기는 위험은 클라이언트 모델이 원문에 없는 내용(다른 커넥터에서 가져온 데이터, 지어낸 주장, 숨은 지시)을 공유 위키에 넣는 것이다. 다음 네 단계로 위험을 줄인다. 사실성이나 인젝션 부재를 보장하지 않는다.
  1. **자유 Markdown을 받지 않는다.** `submit_window`는 구조화된 기여 JSON(개념 이름, 문장, 문장별 블록 참조 `[doc:B0001]`, 링크)만 받는다. 페이지 본문은 서버가 기존 템플릿으로 조립한다.
  2. **출처를 검증하고 근거 없는 기여를 줄인다.** 모든 문장은 블록 참조와 근거 인용 필드를 가져야 한다. 참조는 고정 스냅샷의 해당 window 안에 있어야 하고, 인용은 참조 블록 원문의 부분 문자열인지 정확히 검증한다. 생성 문장과 인용의 어휘 겹침 기준은 보조 휴리스틱이다. 부정어를 빼거나 원문을 선택적으로 엮는 왜곡은 통과할 수 있고, 정확한 의역·번역은 거절될 수 있다. 이를 원문 밖 내용의 완전한 차단으로 표현하지 않는다.
  3. **지시형 문장과 외부 링크를 막는다.** 명령형·역할 지시 패턴과 외부 링크·이미지가 있는 기여를 거절하고, `ai_markdown_sanitizer`를 적용한다.
  4. **사람이 승인하고 되돌릴 수 있게 한다.** window 결과는 draft에만 쌓는다. `finalize_ingest`는 위키에 바로 반영하지 않고 웹앱에 편입 미리보기(source 페이지의 전후 차이, 개념별 추가·수정·삭제 문장, 옛 근거 무효화, 삭제되는 페이지, 항목·링크·참조 변경)를 만든다. 생성 문장 옆에 원문 인용을 보여 준다. `wiki.ingest` 권한자가 고정된 draft를 승인해야 위키에 한 번에 반영한다. 반영 뒤에는 기여 원장으로 작업 단위 복구가 된다.
- **재편입의 전체 변경을 승인한다.** 기존 `_rebuild_invalidated_pages`와 `_prune_dangling_references`는 옛 근거 무효화·페이지 삭제뿐 아니라 다른 페이지의 참조까지 연쇄 정리한다. 새 기여가 없는 페이지와 연쇄 변경도 미리보기·승인 해시에 포함한다. 미리보기와 반영은 기존 기여 재생·참조 정리 규칙을 공유하며 별도 알고리즘을 만들지 않는다. 반영 직전 기존 개념 잠금과 ai_db 트랜잭션 안에서 영향 범위를 다시 계산해 전체 변경 집합의 해시와 관련 공개 상태 지문을 승인된 값과 비교한다. 대상이 추가·삭제되거나 결과·기준 상태가 다르면 반영하지 않고 새 미리보기·승인을 요구한다. 승인 API에서 같은 잠금을 잡고 전체를 재계산하지 않으며 사용자 검토 동안 잠금을 유지하지 않는다. 미리보기 상한에는 삭제·구조 변경 항목도 포함한다.
- **원격 기여 원장을 ai_db 잠금으로 보호한다고 가정하지 않는다.** 현재 `read_contributions`는 document-svc HTTP 조회이고, `with_pending_contributions`의 대기 기록은 편입 경로를 보완한다. 반영 계산에서는 원격 원장과 대기 기여를 대사한 입력을 고정해 사용하며, 최신 원격 원장과 ai_db의 분산 원자성을 주장하지 않는다. 수동 편집·lint·복구까지 포함하는 아래 공통 공개 계약에서 ai_db 공개 상태와 계산 입력의 정합성을 확인해야 하며, 누락·불일치가 해소되지 않으면 반영을 보류한다. 미리보기 구현에 SQL 롤백 dry-run을 강제하지 않는다. 이를 선택하려면 본문 외 operation artifact·journal·callback·캐시 등 트랜잭션 밖 효과도 격리되고 기존 객체를 덮어쓰지 않음을 먼저 검증한다. DB 롤백만으로 외부 효과가 취소됐다고 취급하지 않는다.
- 승인 피로를 줄이도록 변경 요약과 검토가 필요한 항목(새 개념, 다른 문서 기여가 있는 개념의 변경, 기준은 통과했지만 근거 겹침이 낮은 문장)을 먼저 보여 준다. 미리보기 문장 수·분량에 상한을 두며 초과 결과는 일부만 보여 준 채 승인받지 않는다. 원문을 별도 문서들로 나눠 각각 새 run으로 편입하거나 기존 웹 편입을 사용하게 한다. 같은 문서의 window 일부를 독립 run으로 나누면 재편입 대체 규칙과 충돌할 수 있으므로 허용하지 않는다. 초기에는 전체 거절 후 새 제안만 지원하고, 항목별 수정·거절과 draft 해시 재생성은 후속 범위로 둔다.
- 개념 동일성은 서버가 제목·별칭의 이름 키(`name_key`)로 결정적으로 판정한다. `canonical_slug`는 판정 결과의 병합 대상 필드이며 병합 규칙이 아니다. 클라이언트가 제출한 대상이나 `slugify` 결과의 일치만으로 병합하지 않고, 후보의 slug도 제목·별칭 일치의 대체 근거로 사용하지 않는다. 이름 일치가 모호하면 새 개념으로 두며, 애매한 병합(Jev·LLM 판단)은 하지 않는다.
- slug에서 파생된 별칭도 개념 동일성의 근거로 쓰지 않는다. `merge_concept_ledger`의 원래 slug와 승격의 cluster ID처럼 기계적으로 추가한 값은 이름 비교용 별칭과 구분한다. 기존 별칭의 출처를 구분할 수 없으면 해당 별칭만으로 자동 병합하지 않는다. 링크 해석에 필요한 기존 값은 보존하되 이름 비교에서는 제외하며, 제목 자체의 일치는 유지한다. 과거 페이지를 읽는 경로에도 이 규칙을 적용한다.
- 서로 다른 개념의 slug가 충돌하면 별도 slug를 배정하고 기여·근거·링크에 같은 매핑을 적용한다. 작업 안 정규화의 slug 키 병합 및 근거 힌트 매핑, 판정 입력의 같은 slug 후보 제외, `create_new`의 slug 확정, post_ingest 승격의 대상 선택(`_core_concept_promotions`의 slugify 이름 비교)과 생성 slug 충돌 병합, 저장소의 slug 충돌 갱신까지 점검해 slug만으로 개념이 합쳐지지 않게 한다. 웹·MCP 공통 경로의 이 보완을 4단계에 포함한다. 이미 합쳐진 과거 데이터의 자동 분리는 이번 범위에 포함하지 않는다.
- slug 배정은 기존 항목 분리의 후보 선택 규칙을 재사용·공통화하고 개념 잠금 안에서 확정한다. 후보를 모두 소진하면 기존 개념에 합치거나 덮어쓰지 않고 명시적으로 실패한다. 미리보기와 반영은 같은 배정 규칙을 쓰며, 동시 변경으로 배정 결과가 달라지면 기존 전체 변경 해시 검증에 따라 새 미리보기와 승인을 요구한다.
- slug 점유 판정에는 논리 삭제된 페이지도 포함한다. 다른 개념의 삭제 페이지는 slug가 같아도 그 page_id를 재사용하거나 되살리지 않는다. 활성 페이지에 이름 일치 대상이 없고, 같은 workspace의 삭제 페이지 중 위 이름 규칙으로 동일성을 확인한 대상이 하나뿐이면 기존 page_id·slug를 재사용해 되살리는 현행 재편입 동작을 유지한다. 삭제 후보가 모호하면 어느 삭제 page_id도 되살리지 않고 새 개념으로 두며, 위 후보 선택 규칙에 따라 새 slug를 배정한다. 이 경우 삭제 페이지의 수동 링크는 넘겨받지 않는다. 웹 수동·자동 편입과 MCP에 같은 규칙을 적용한다. 부활에 따른 수동 링크 등 전체 변경도 미리보기·승인 해시와 반영 직전 재검증에 포함한다. 파기된 사용자·workspace 데이터에는 이 부활 규칙을 적용하지 않는다.
- `submit_lint_changes`는 기존 lint reconciliation의 작업 유형을 닫힌 목록으로 받는다. 개념 병합·링크 정리·고아 페이지 처리 등 구조 변경에는 유형별 대상·참조·정합성 검증을 적용하고, 새로 추가하거나 바꾸는 문장에는 위 1~3의 기여·인용 검증을 적용한다. 문장이 없는 구조 변경에 문장별 인용을 요구하지 않는다. 근거 범위는 해당 lint run에 서버가 허용한 원문 스냅샷 집합으로 제한한다. 대상 페이지 ID·버전/내용 해시 집합을 고정하고 승인과 반영 시 재검증한다. 하나라도 바뀌면 전체를 거절하며 모든 작업에 4의 웹 미리보기 승인을 적용한다.
- 최종 반영은 기존 `concept_write_lock`과 기여 재조립 규칙을 재사용하되, 본문 공개 방식은 변경한다. 현재 저장 경로는 고정 S3 키를 덮어쓰므로 ai_db 트랜잭션만으로 원자적 반영이 되지 않는다. 객체 변경 journal도 사후 복구 수단이지 DB와 S3의 원자적 커밋이 아니다.
- **새 본문은 변경 불가능한 새 객체 키에 저장하고 DB 커밋으로 공개한다.** 잠금 안에서 대상 페이지와 draft를 재검증하고 최종 본문을 조립·저장한 뒤, source·concept의 본문 참조·링크·기여·반영 상태·결과 outbox를 하나의 ai_db 트랜잭션으로 커밋한다. 조회·검색·임베딩은 커밋된 참조만 사용한다. 업로드 실패나 DB 롤백 시 기존 공개 참조를 유지하며, 미공개 객체는 정리한다. 정리 작업은 진행 중 업로드와 현재 페이지·복구 이력이 참조하는 객체를 삭제하지 않는다. 여기서 원자성은 S3 업로드와 DB 커밋의 분산 원자성이 아니라 결과의 공개 경계다.
- 웹 편입(수동 및 업로드/변환 후 자동 편입)·수동 편집·lint·복구도 같은 잠금 및 본문 참조 계약을 따르도록 공통 저장 경로를 갱신한다. 기존 고정 키는 읽기 호환을 유지하되, 이후 변경은 새 키를 만들며 과거 본문을 덮어쓰지 않는다. 복구도 현재 기여를 재조립한 새 본문 참조를 공개하고, 기존 journal이 공유 객체를 덮어써 이 계약을 우회하지 않도록 한다. 이 전환과 객체 보존·파기 규칙은 4단계 출시 조건이다. 문서별 활성 run 제한은 workspace 단위 개념 잠금을 대체하지 않는다.
- **원문 정합성의 한계:** 기존 `RunPipelineUseCase._ensure_current_source`의 document-svc 조회를 승인 및 반영 직전에 재사용한다. 원문 조회와 ai_db 커밋은 서로 다른 서비스여서 원자적이지 않다. 최종 조회 이후 원문이 바뀌는 경합은 기존 `document.edit.event`의 revision 역행 방지와 파생물 stale 판정으로 수렴시킨다. 이는 원문 버전이 영원히 최신이라는 보장이 아니라 고정 스냅샷 편입과 이후 stale 표시다. 엄격한 분산 잠금·2PC는 도입하지 않으며 이 경합과 이벤트 선행·지연 도착을 테스트한다. lint 대상 위키 페이지 비교·반영은 동일 ai_db 잠금·트랜잭션 안에서 수행한다.
- 반영 뒤 post_ingest lint를 서버 LLM으로 돌리면 그 부분은 웹 경로와 같이 크레딧을 차감한다. 클라이언트가 lint tool로 직접 하면 수수료만 받는다.

### 멱등·결과 전달

- `start_ingest`, 편집·계획 제안, window·lint 제출, finalize·반영에는 멱등 키를 둔다. 범위는 grant·user·workspace·tool과 대상 run/window다. 인가를 먼저 수행한 뒤 이전 결과를 조회한다. 같은 키·같은 정규화된 내용은 이전 결과를 반환하고, 같은 키·다른 내용은 충돌로 거절한다. 동시 재시도도 DB 유일 제약으로 한 번만 수락한다.
- 멱등 키 기록이 만료돼도 승인·반영의 도메인 키(run·plan/draft version·operation ID)로 같은 실행을 다시 반영하거나 청구할 수 없게 한다. 응답이 유실되면 새 실행을 만들지 않고 기존 handle로 상태를 확인한다.
- 위키 반영 상태와 결과·정산 이벤트는 **같은 ai_db 트랜잭션**에 기록한다. 기존 ai_db `analytics_outbox`/relay 패턴을 참고하되 과금 전달은 재전달과 미정산 대사가 가능한 내구성을 갖춘다. document DB의 outbox만으로 ai_db 반영까지 원자적으로 묶였다고 취급하지 않는다.
- Agent 계획은 각 작업이 document DB에 따로 커밋된다. 문서 변경과 실행 영수증(operation ID·approval ID·실제 변경 여부)은 같은 document DB 트랜잭션에 기록하며, document-svc가 이를 정산의 기준으로 삼는다. ai-svc의 종료 상태는 정산을 시작하는 신호일 뿐 청구 증거가 아니다. 별도 트랜잭션의 `prepareToolApply` 준비 기록은 커밋 영수증이 아니다. 기존 24시간 응답 멱등 캐시와 별도로 영수증을 정산·중복 방지 보존 계약에 따라 유지한다. 응답 유실·실행 결과 미확인은 재조회·대사 후 확정하며, 메시지 전송 실패를 실행 실패로 바꾸지 않는다.
- **실행 결과 미확정은 모든 시도 이력과 영수증으로 판정한다.** 예산 소진 자체는 호출 전 검사지만 직전 시도는 이미 반영됐을 수 있다. 타임아웃·전송 오류·재시도 가능 오류·`IDEMPOTENCY_IN_PROGRESS` 또는 응답 없는 실행 기록이 있고 확정 결과가 없으면, 마지막 오류가 409이거나 run이 `failed`·`conflicted`여도 미실행으로 단정하지 않는다. 미착수와 미확정은 작업별 사유와 대사 상태로 구분해 API·UI에 표시한다. 서비스 인증된 읽기 전용 영수증 조회(workspace·사용자·approval·operation 범위)를 사용하며, 새 변경을 일으킬 수 있는 execute 재호출로 대사하지 않는다. 기존 execute는 멱등 응답 재사용보다 run 인가가 먼저라 종료 후 재호출도 대사 수단이 될 수 없다. run 종료와 정산 완료는 분리하고, 영수증 부재만으로 진행 중 요청의 미실행을 확정하거나 예약을 해제하지 않는다.
- **미확정 생성 작업의 중복 재실행을 막는다.** `create_document`·`create_folder`에는 기존 대상의 `base_version`이 없어 새 제안의 충돌 검사만으로 중복 생성을 막지 못한다. 제안 제출 전체를 막지 않고, 서버가 같은 workspace·사용자의 미확정 생성 작업과 tool·실제 목적지·정규화한 이름 또는 내용 해시를 대조해 중복 후보를 판정한다. 클라이언트의 선행 작업 연결 선언에 의존하지 않으며, 미해결 후보가 있으면 해당 작업의 실행을 보류한다. 대사 뒤 실패가 확정되면 새 승인 범위에서 실행하고, 이미 성공했다면 기존 결과를 안내한다. 이름·내용이 다른 생성까지 동일 의도라고 추론하는 일반 중복 탐지 기능은 추가하지 않는다.

### 과금

- **A안: 성공한 승인 변경 1건당 고정 단가를 적용하고 계획당 상한을 둔다.** 과금 대상 변경은 사용자가 승인한 계획의 operation이며, 검색·조회·검증·내부 재시도 같은 tool 호출은 세지 않는다. 부분 승인은 선택한 operation만 대상이다. 단가와 상한 값은 미결이다.
- 승인 화면에 선택한 작업 수 N, 건당 단가, 계획당 상한과 최대 청구액 `min(N × 단가, 계획당 상한)`을 보여 준다. 실제 청구액은 `min(성공한 승인 변경 수 × 단가, 계획당 상한)`이다. 승인 범위·단가·상한·가격 버전을 고정하며 실패 작업을 추가해도 성공 작업의 단가는 내려가지 않는다.
- 상한은 고정된 승인 범위(approval ID)별로 적용한다. 여러 계획을 따로 승인하면 각각 청구되며, 대화 전체의 합산 상한이 아님을 승인 화면에 표시한다.

| 실행 결과 | 플랫폼 수수료 |
|---|---|
| 제안·승인만 하고 미실행, 실패·충돌·취소·관리자 중단으로 성공한 변경이 없음 | 없음 |
| 승인 범위 전체 성공 또는 일부 성공 후 실패·취소·관리자 중단 | 실제 성공한 승인 변경 수 × 고정 단가, 계획당 상한 적용 |
| 성공한 변경을 이후 취소·역순 복구·되돌리기로 제거 | 이미 성공한 변경의 수수료는 환불하지 않음. 실행 완료 여부와 무관하게 동일 적용 |
| 실행 응답 유실·검증 실패 등 실제 성공 여부가 불명확함 | 정산 보류 후 실행 영수증으로 대사. 상태 이름만 보고 청구 여부를 단정하지 않음 |

- 성공 여부는 단순히 `run.status`나 현재 남은 결과가 아니라 커밋된 operation 실행 영수증으로 확인한다. 동일 operation의 재전달·재시도는 한 번만 센다. 사용자의 후속 편집·복구는 이미 성공한 변경 수를 줄이지 않는다. 복구 작업 자체는 원래 승인 변경 수에 추가하지 않는다. 미완료 실행의 전부 복구 시 무료라는 예외는 두지 않는다.
- 같은 이름으로 rename하는 등 실제 변경이 없는 operation은 성공 응답이어도 무료다. 제출 시 명백한 무변경 operation이 하나라도 있으면 해당 항목을 알려 제출 전체를 거절하고 재제출받는다. 실행 시에는 영수증의 `changed`로 판단한다. 기존 worker의 `succeeded` 상태만으로 과금하지 않는다.
- 승인 재시도에는 같은 approval ID를 사용하고, 원본 operation ID의 유일 제약과 승인별 누적 청구액 잠금으로 중복 집계·상한 초과를 막는다. 기존 `CreditService.settle`의 누적 청구액 기반 멱등 패턴을 재사용한다. `partial_failed`·`halted` 이후 복구를 거쳐 다시 종료돼도 같은 승인을 재청구하지 않는다. 결과가 미확정인 operation이 있으면 첫 종료 알림만으로 최종 정산하지 않는다.
- 복구 때문에 환불하지 않는 것과 오청구 정정은 다르다. 대사에서 실패한 작업을 청구했거나 중복 청구한 사실이 확인되면 원장에 조정 기록을 남긴다. 복구 실패만으로 이미 확인된 원래 실행의 정산을 보류하지 않는다.
- 편입은 원자적으로 반영된 1건(고정 원문 분량 기준), lint는 원자적으로 반영된 1회로 청구한다. draft 제출·거절·미반영은 무료다. 원문 경합으로 나중에 stale이 된 성공 편입이나 반영 후 사용자 복구(`wiki.restore`)는 수수료 환불 사유가 아니다.
- 무료 제안 수락 시에는 권한·사용 한도·활성 제안 수를 확인한다. 웹 승인 시 최대 청구액 전액을 확보하지 못하면 402로 거절한다. 기존 크레딧 계정 잠금·원장은 재사용하되, `CreditService.admit`의 `min(estimate, available)` 부분 예약 규칙은 MCP에 적용하지 않는다. 승인 ID에 묶은 예약을 먼저 커밋하고 ai-svc에 같은 ID로 승인을 전달한다. 예약 없는 실행은 시작하지 않고, 정산 시 실제 청구액만 차감한 뒤 남은 예약을 해제한다. 실행하지 않았거나 성공 변경이 없음을 확인하면 전액 해제한다.
- document-svc는 승인된 MCP run을 주기적으로 조회·대사해 종료와 미확정 결과를 확인한다. 사용자의 웹 상태 조회나 단발성 종료 알림에 정산을 의존하지 않는다. MCP 수수료 예약은 기존 `releaseStale`의 시간 경과에 따른 자동 정산·해제 대상에서 제외하고, 영수증 기반 대사와 정해진 미확정 처리 계약으로 해제한다. 모델 `usage_charges`의 `collectPending`과 섞이지 않도록 예약·청구 유형을 구분한다. 이 경로는 2단계 출시 조건이다.
- 기존 `AgentTurnService.rerun`은 원격 전달 실패만으로 run 단위 예약을 해제하지 않는다. 응답 유실 시 예약을 유지하고, 그 외 오류는 `reconcileFailedForward`에서 종료 여부를 재조회한다. 이 예약 유지 원칙과 기존 응답 유실·5xx·409 테스트를 재사용한다. MCP에서는 안정된 approval ID에 묶인 수락·실행 대사와 수수료 정산으로 확장하며, 기존 run 종료 상태나 `releaseStale`만으로 수수료 예약을 해제하지 않는다. 성공 변경분을 정산하고, 미확정 작업은 실행되지 않았고 앞으로도 실행될 수 없음을 확정한 뒤 미사용 예약을 해제한다. 취소된 승인 ID의 지연 요청은 enqueue할 수 없게 하며, document의 변경 경계에서도 예약 유효성을 검사한다. 정산 보류의 예약 해제·조정·대사 기한은 구현 계약에 명시한다.
- **모델 사용량과 플랫폼 수수료 원장은 분리한다.** 기존 ai-svc `/usage`는 provider·모델·토큰 사용량 계약을 유지한다. 문서 변경은 document의 실행 영수증으로, 위키 반영은 ai-svc의 원자적 결과 이벤트로 확인한다. 수수료 원장·단가·크레딧 차감·조정은 document-svc가 소유한다. 기존 Agent 종료 정산 경로는 서버 모델 사용량과 MCP 수수료를 구분해 중복 청구를 막는다. 원장 분리는 결정 사항이며 테이블·이벤트 스키마만 후속 구현에서 정한다.
- 서버 LLM으로 수행한 post-ingest lint 등 모델 비용은 플랫폼 수수료와 별도다. 클라이언트가 수행하는 lint는 반영 수수료만 대상이다. 서버 모델 작업을 함께 실행할 경우 승인 화면에서 별도 비용과 실행 여부를 고지한다.
- 읽기 tool은 결과 단위로 셀 수 없다(서버는 클라이언트가 답변을 썼는지 모른다). 수수료 대상에서 빼고 사용자별 일일 호출 한도로 묶는다. 읽기를 요금제에 포함할지는 미결이다.

### 상태 보관·파기

- 사용자·workspace별 활성 run·draft·제안 수와 총 저장량 상한을 둔다. 진행이 없는 draft는 만료시키고 스냅샷·artifact·잠금을 정리하되 완료된 실행의 중복 방지·정산에 필요한 기록은 보존 정책에 따른다.
- ai ADR 0029의 user·workspace 파기 대상에 MCP run·draft·스냅샷·artifact·멱등 기록을 포함한다. 생성·재시도·반영·지연 이벤트 처리에서 `ai_purged_scopes`를 검사해 파기된 데이터를 되살리지 않는다. access는 관련 grant를 폐기한다. document의 수수료 원장·outbox·감사 기록도 기존 파기 및 보존 계약에 맞추며 본문을 담지 않는다.
- 파기 시 새 실행을 차단하고 진행 중 실행을 확인한 뒤 확정분을 정산하고 미사용 예약을 해제한다. 미확정 결과는 보존이 허용된 본문 없는 최소 정산 증빙으로 대사한다. 파기 요청만으로 자동 무료 처리하거나 예약을 무기한 유지하지 않는다. 증빙의 보존 범위·기한과 보존 불가/기한 만료 시 미확정 건의 처리 정책은 2단계 출시 전에 확정한다.

- **T1. tenant 격리**
  - workspace·user는 tool 인자로 받지 않는다. 검증된 access token과 활성 grant의 일치하는 문맥에서만 결정한다. 문서·페이지 ID로 조회할 때도 매번 소유 workspace를 검사한다.
  - document-svc가 ai-svc를 호출할 때 확인된 workspace·user·grant 문맥을 넘긴다. ai-svc는 받은 ID를 그대로 믿으므로 **document-svc의 인가 누락은 곧 tenant 유출이다.** ai-svc의 MCP용 내부 API는 모든 쿼리에 workspace 조건을 건다.
  - 다른 workspace의 ID로 모든 tool을 호출하는 교차 tenant 테스트를 document-svc 경계에서 배포 전 필수 검사로 둔다.
- **T2. 사용자 권한으로만 실행**
  - tool은 서비스 권한이 아니라 **요청한 사용자의 권한**으로 실행한다. 웹 경로와 같은 판정 메서드를 쓴다: 멤버 여부(`requireMember`), 권한 항목(`requirePermission`의 `wiki.ingest`·`wiki.lint`), 문서 편집 권한(`DocumentAccessPolicy`).
  - OAuth scope를 `read`·`write_propose`·`wiki_write`로 나눈다. scope는 사용자가 클라이언트에 허락한 범위일 뿐이며, 실제 권한은 매 호출 access 권한 항목으로 다시 판정한다.
  - 쓰기 tool은 필요한 scope가 없으면 HTTP 403과 `WWW-Authenticate: Bearer error="insufficient_scope", scope="<필요한 scope>", resource_metadata="<메타데이터 URL>"`로 답해 그 시점에 추가 동의를 받는다(step-up). MCP 2025-11-25의 권고 응답 형식을 이 서비스의 계약으로 채택하며, JSON-RPC tool 오류만으로 대체하지 않는다. workspace 관리자가 허용한 scope만 동의 화면에 노출한다.
- **T3. OAuth와 토큰**
  - MCP access token의 `aud`는 MCP 서버 URI다(RFC 8707). **audience를 양방향으로 분리한다.** 기존 웹 API는 MCP 토큰을 거부하고(`aud=fruition-api`만 허용), MCP 엔드포인트는 웹 토큰을 거부한다.
  - 서명·`iss`·`aud`·만료·scope를 매 요청 암호학적으로 검증한다. 형식만 보지 않는다. 잘못된 서명, 만료, 다른 audience, 다른 issuer 토큰이 모두 401인지 확인하는 계약 테스트를 매 배포 돌린다.
  - MCP access token을 ai-svc나 다른 서비스로 전달하지 않는다(token passthrough 금지). 내부 호출은 기존 서비스 토큰과 확인된 사용자 문맥으로 한다.
  - **state handle은 인증 근거가 아니다.** `run_id` 같은 handle은 추측할 수 없는 난수로 만들고, 서버 쪽에서 workspace·user·원래 grant에 묶는다. MCP 요청은 다른 grant의 handle을 사용할 수 없다. 웹 승인은 기존 사용자 및 역할 권한과 grant 정책을 함께 적용한다. 웹 이력 조회·취소·복구는 기존 사용자·역할 권한으로 검사하며 활성 MCP grant를 요구하지 않는다. 다른 사용자의 handle로 들어온 요청은 존재하지 않는 것으로 답한다. 기존 Agent run 조회(`get_current_plan_for_user`)와 새 MCP run·draft 테이블 모두 소유 범위를 검사한다.
  - **전송 세션도 별도로 격리한다.** SDK의 `Mcp-Session-Id`를 사용하는 경우 서버가 검증된 user·workspace·grant에 세션을 묶고, POST뿐 아니라 지원하는 GET 재접속·DELETE에서도 토큰·현재 grant·세션 소유권을 검사한다. 세션 ID만으로 인증하지 않는다. SSE 재전송을 지원하면 `Last-Event-ID`와 재전송 버퍼에도 같은 소유 범위를 적용하고, 회수된 grant나 다른 세션의 이벤트를 반환하지 않는다. 이를 위해 SSE 재전송 기능을 새로 추가할 필요는 없다.
  - access token 수명을 짧게 하고 refresh token을 회전한다. 웹앱에 연결된 클라이언트 목록과 회수 기능을 둔다. MCP의 멤버 탈퇴·권한 변경 판정은 기존 권한 projection 무효화에 의존하지 않고 원본 저장소를 확인한다. 기존 웹 경로의 projection 무효화는 유지한다. 연결 해제·관리자 MCP 비활성화를 포함한 판정과 실행 경계는 [grant와 연결 회수](#grant와-연결-회수)를 따른다.
- **T4. 프롬프트 인젝션과 유출 경로 차단**
  - 서버가 막을 수 있는 유출 경로는 **우리 쓰기 tool**이다. 문서 쓰기와 위키 쓰기(ingest·lint) 모두 제안만 만들고, 웹앱에서 사람이 미리보기를 보고 승인해야 반영된다.
  - 위키 쓰기는 공유 위키를 통한 저장형 인젝션 경로가 되므로 [MCP ingest](#mcp-ingest)의 네 겹 방어를 적용한다.
  - tool 응답의 문서·위키 내용은 데이터 경계 표시로 감싸고, 외부 링크·이미지를 무력화한다([0028](0028-ai-output-external-link-neutralization.md)). 응답 크기와 검색 결과 수에 상한을 둔다.
  - 사용자 클라이언트에 연결된 다른 커넥터로 새는 것은 서버가 막을 수 없다. workspace 관리자 허용(기본값 꺼짐)과 허용 화면의 위험 고지로 책임 범위를 명확히 한다. 문서·폴더 단위 MCP 제외는 두지 않는다. 개념 페이지가 여러 문서를 합성하므로 원문을 막아도 `search_wiki`로 내용이 나가 실효가 없다.
- **T5. SSRF 차단:** 어떤 tool도 URL·호스트·파일 경로를 인자로 받지 않는다. 인자는 ID, 검색어, 요청 문장, Markdown 본문, 구조화된 기여 JSON뿐이다. ID는 종류별 기존 계약으로 검증한다. 문서 ID는 `doc_`·`chatdoc_`를 포함하는 기존 문자열 ID 검증과 길이 상한을 재사용하고, 폴더·run 등 UUID인 식별자만 UUID로 검증한다. operation ID·블록 참조 등도 각 도메인의 형식을 유지한다. 형식 검증 뒤에는 소유 workspace와 접근 권한을 별도로 검사한다. 서버가 외부로 요청을 보내는 tool은 만들지 않는다. access의 CIMD 조회는 별도 외부 요청 경계이며 [인증](#인증)의 조회 전 허용 목록 검사와 네트워크 제한을 적용한다.
- **T6. tool 정의 고정**
  - tool 이름·설명·입력 스키마는 코드에 고정하고 리뷰를 거쳐 배포한다. 사용자나 workspace가 만든 텍스트(문서 제목, Skill 이름·본문)를 tool 정의에 넣지 않는다.
  - tool 정의를 바꾸면 버전을 올리고 변경 내역을 공지한다.
  - 팀 Skill을 MCP로 노출하지 않는다. workspace 멤버가 쓴 지시가 다른 멤버의 클라이언트 모델에 지시로 들어가는 경로가 되기 때문이다.
- **T7. 주입 방지:** MCP 서버는 shell·외부 프로세스·파일 시스템 경로를 사용하지 않는다. 업로드·첨부 tool을 두지 않는다. DB 접근은 기존 저장소 계층의 파라미터 바인딩만 쓴다. 모든 tool 입력은 JSON 스키마로 검증하고 길이 상한을 둔다. 요청 본문은 4 MiB로 제한한다.
- **T8. 노출 최소화:** MCP 데이터·tool 경로는 익명 접근을 허용하지 않는다. 인증 전 discovery metadata 조회와 OAuth 로그인·코드 교환의 진입은 해당 프로토콜에 필요한 범위로 허용하되, 로그인·동의·코드/refresh 검증을 생략하는 예외로 쓰지 않는다. Streamable HTTP의 `Origin` 헤더를 검증하고 HTTPS만 허용한다. 사용자·workspace·클라이언트 단위로 rate limit과 일일 호출 한도를 건다. 사용자 식별 전의 OAuth 진입점에도 IP별 요청량과 전체 동시 처리량 제한을 적용하며 CIMD 조회 전에 제한한다.
- **T9. 공급망:** 공식 MCP Java SDK와 Spring Authorization Server의 버전을 고정하고, 의존성 취약점 스캔과 보안 공지 모니터링 대상에 넣는다.
- **감사:** 모든 tool 호출을 사용자·workspace·클라이언트·tool·대상 ID·결과와 함께 실행하는 서버 쪽에서 기록한다. 본문은 기록하지 않는다. 모든 쓰기 결과에 작성자와 MCP 경로를 남기고, 기존 AI 이력에서 되돌릴 수 있게 한다.

### 단계

0. access 인가 서버·grant: 인증 전 discovery와 PKCE metadata, 동의 문맥에 묶인 일회용 인가 코드·resource 검증, 동의 화면 보호·loopback 경고, 조회 전 CIMD 허용 목록 검사·인증 전 요청 제한, refresh 재사용 탐지·보안 회수, MCP audience 토큰, workspace 선택, 연결 목록·회수 UI, 클라이언트별 호환성 검증. 1단계의 전제다.
1. 읽기 전용: `search_wiki`·`get_wiki_page`·`find_documents`·`get_document`. 검색 전용 내부 API를 추가하고 페이지·문서 조회는 기존 API·서비스를 재사용한다. 쓰기 tool은 목록에도 노출하지 않는다. 관리자 허용, 교차 tenant·토큰·grant 회수 검사, 캐시에 의존하지 않는 현재 멤버십·권한 판정, 식별자 종류별 검증, 감사 로그를 포함한다.
2. `propose_document_edit`: 공통 결정적 검증, MCP 자동 승인 차단과 명시적 웹 승인·버전 충돌, 멱등, 관리자 중단(`halted`)과 기존 취소·복구의 구분을 먼저 완성한다. 승인 및 변경 직전의 현재 권한 재검증을 포함한다. A안의 단가·상한을 확정하고, 승인 시 최대 청구액 전액 예약·안정된 승인 ID·실제 변경 영수증·수수료 원장·결과 전달·대사와 파기 시 미정산 처리 계약을 출시 조건에 포함한다.
3. `propose_plan`: 폴더·문서의 다단계 변경, 부분 승인·부분 실패 과금, 호출 예산·단계 한도 소진의 종료·대사, 관리자 중단과 기존 복구 경로를 검증한다.
4. ingest·lint: 고정 원문 스냅샷, 구조화 기여, 원문 인용 대조, draft 미리보기 승인, 변경 불가능한 본문 객체와 DB 참조의 원자적 공개·outbox, 파기·취소·복구. 수동 편입·업로드/변환 후 자동 편입·수동 편집·lint·복구의 공통 저장 경로 전환을 포함하며, MCP 어댑터 추가가 아니라 새 실행 경로 개발로 산정한다. 편입의 고정 원문 분량 산정 단위·가격 구간 또는 산식과 lint 반영 단가를 확정하고, 승인할 draft에 분량·가격 버전·최대 청구액을 고정한다. 승인 시 전액 예약·원자적 결과 이벤트 기반 정산·미반영 확정 시 예약 해제를 출시 조건에 포함한다.

### 출시 전 필수 계약 테스트

각 검사는 해당 기능을 공개하는 단계의 출시 조건이다. 읽기 전용 출시를 아직 제공하지 않는 쓰기·편입 기능의 구현과 테스트 완료에 종속시키지 않는다.

- 모든 tool·cursor·handle·멱등 키의 교차 tenant/사용자/grant 접근, 잘못된 서명·issuer·audience·만료·scope, 연결 회수 및 관리자 차단. 사용자 연결 해제와 관리자 중단의 승인 전후 동작을 구분한다.
- 읽기 출시 전: 토큰 없이 discovery metadata를 조회할 수 있고 MCP 데이터·tool 요청은 401인지 확인한다. PKCE metadata, 인가 코드의 만료·재사용·동시 교환, 잘못된 verifier, client·redirect(인가 요청의 loopback 포트 포함)·resource 바꿔치기를 검사한다. 동의한 사용자·workspace·scope가 토큰 교환으로 바뀌지 않으며, 인증 전 요청 제한이 CIMD 조회보다 먼저 적용되는지 확인한다.
- 읽기 출시 전: 전송 세션을 사용하면 자신의 정상 토큰과 다른 사용자·workspace·grant의 세션 ID를 조합한 POST·지원하는 GET/DELETE를 거절하는지 검사한다. SSE 재전송을 지원하면 다른 세션의 이벤트 ID 및 회수된 grant로 이벤트를 재조회할 수 없는지도 확인한다.
- scope 부족 응답이 HTTP 403과 `WWW-Authenticate`의 `error`·`scope`·`resource_metadata`를 포함하는지 검사한다. 읽기 scope 검사는 1단계, 쓰기 step-up 검사는 해당 쓰기 단계에 포함한다.
- 읽기 출시 전: 이전 권한 캐시를 남기고 무효화를 실패시켜도 탈퇴한 멤버의 읽기를 차단하는지 검사한다. 쓰기 단계에서는 권한·OWNER 역할 회수 후 제안·웹 승인·다음 변경을 차단하는지 확인한다. access 확인 실패 시 캐시로 허용하지 않으며, 사용자 연결 해제만 한 기존 승인 실행은 현재 권한이 있으면 계속되는지도 검사한다.
- 읽기 출시 전: 실제 `doc_`·`chatdoc_` ID로 검색 후 본문을 조회할 수 있고, 잘못된 형식·과대 길이·다른 workspace의 ID는 거절하는지 검사한다. 쓰기 단계에서는 같은 ID로 편집을 제안하고 폴더·run·operation·블록 참조의 각 형식도 검증한다.
- 읽기 출시 전: 미등록 CIMD URL에는 네트워크 요청이 발생하지 않는지, redirect·내부 주소·과대 응답을 차단하는지, 클라이언트별 redirect를 섞어 사용할 수 없는지 검증한다. loopback 동의 화면의 호스트·앱 신원 미검증 경고와 동의 화면의 클릭재킹·CSRF 방어를 확인한다.
- 읽기 출시 전: 탈취자가 먼저 refresh한 뒤 옛 토큰이 재사용되면 후속 refresh token과 해당 grant의 access token이 모두 차단되는지 검증한다. 동시 갱신·응답 유실 후 재시도·오류 응답 후 폐기 영속성·임의 무효 토큰의 타 grant 회수 불가도 검사한다. 보안 회수 후 승인 실행 중단은 쓰기 단계에서 검증한다.
- 각 쓰기 출시 전: 악성 HTML·외부 이미지·링크가 포함된 본문·제목·인용으로 미리보기를 열어도 스크립트 실행·외부 이미지 요청·자동 승인이 발생하지 않는지 검증한다. 기존 프런트엔드 CSP·Markdown 렌더링 테스트를 재사용하고 새 화면의 연결을 확인한다.
- 각 쓰기 출시 전: 자동 승인 설정을 켜고 정상 본문의 MCP 제안을 조회하거나 plan-ready 알림을 전달해도 승인 대기로 남는지 검사한다. 자동 승인 API 직접 호출과 출처 위조를 거부하고, 명시적 웹 승인만 실행을 시작하는지 확인한다. 기존 웹 제안의 자동 승인 동작은 유지한다.
- 계획 제출 출시 전: 이름·내용 중복 의심이 필수 검증 실패와 구분되고, 경고 및 의존 작업의 기본 선택 해제가 기존 웹 경로와 같은지 검사한다. 중복 의심만으로 제출 전체를 거절하지 않는다.
- 읽기 출시 전: 저장 벡터가 없는 후보가 많아도 질문 외 본문 임베딩이 발생하지 않고, 후보 조회량·총 텍스트량·처리 시간의 상한이 적용되는지 검사한다. 응답 개수 제한만으로 이 검사를 대체하지 않는다.
- ingest 출시 전: `C`·`C#`·`C++`처럼 slug가 같고 이름 키가 다른 개념이 제출 순서와 무관하게 별도 페이지로 유지되는지 검사한다. 기존 페이지와의 충돌 및 동시 편입에서도 덮어쓰기 없이 기여·링크가 올바른 페이지를 가리키는지 웹·MCP 공통 경로로 검증한다. 삭제된 C가 있는 상태에서 C#을 편입해도 기존 page_id·수동 링크를 넘겨받지 않는지, 동일 개념의 삭제·재편입 반복에서는 page_id·slug가 유지되고 후보를 소진하지 않는지 검사한다. 모호한 삭제 후보가 있을 때 기존 page_id·수동 링크를 넘겨받지 않고 새 페이지가 생기는지 웹 수동·자동 편입과 MCP에서 검증한다. 유일한 동일 개념 후보의 부활로 복원되는 수동 링크의 미리보기 포함도 검증한다. 한 문서 안에 함께 나오는 경우, 기존 페이지에 slug 유래 또는 출처 불명 별칭이 있는 경우, 재편입·post_ingest 승격·slug 후보 소진을 포함한다. 근거 힌트의 매핑과 기존 링크 해석이 유지되고, 미리보기 후 slug 배정이 바뀌면 승인을 다시 요구하는지 검사한다.
- 각 쓰기 출시 전: MCP 예산 소진이 `clarification_required`나 서버 LLM 재계획으로 이어지지 않고 기존 검증·종료 경로를 타는지 검사한다. 20개 작업의 재시도 누적과 일부 성공 후 소진에서 미착수는 skipped, 이미 시도한 미확정 작업은 별도 사유·대사 대상으로 남는지 검증한다. 타임아웃 뒤 `IDEMPOTENCY_IN_PROGRESS` 409, 최종 5xx, 종료 이후 늦은 커밋, 기존 인가·조건부 갱신의 재시작 차단, 24시간 멱등 기록 만료 후 영수증 대사, run 종료와 미정산 예약의 분리를 포함한다. 미확정 create의 선행 연결을 클라이언트가 생략해도 서버가 같은 생성의 실행을 보류하고 무관한 제안 제출은 허용하는지 검사한다. 단계 한도 도달은 진행 불능 오류로 다루고 기존 `test_executor_requests_clarification_when_budget_runs_out_mid_retry`의 웹 동작은 유지한다.
- 플래너를 우회한 대상 ID·인자·artifact 해시/용도·폴더 범위 위조, 승인 후 계획/draft 변경, 원문·페이지 변경 충돌, window 재전송과 동시 finalize.
- 일부 작업 성공 후 실패·취소, 응답 유실 후 재조회, 결과·청구 이벤트 중복 및 순서 역전, 원장 대사와 예약 해제. 단순 성공 상태만이 아니라 operation별 실제 커밋과 무변경 무료 처리, 최대액 미달 예약 거절, 승인 타임아웃·중복 409·예약 해제 후 지연 승인, 웹 조회 없는 종료 정산, 미확정 예약에 대한 기존 `releaseStale` 간섭 방지, 복구로 인한 반복 종료 알림, 중복 집계 방지, 승인별 상한, 복구 후에도 성공 변경 수 유지 여부를 검증한다.
- 수동 편입·업로드/변환 후 자동 편입과 MCP 편입 동시 실행, 수동 편집/lint와 개념 잠금 경쟁, 원문 최종 조회 직후 편집 및 이벤트 선행·지연 도착, 만료·파기 후 재시도와 지연 이벤트가 데이터·청구를 되살리지 않는지 확인한다.
- ingest 출시 전: 재편입으로 옛 근거·항목·링크가 제거되고 마지막 근거가 사라진 페이지가 삭제되는 경우, 새 기여가 없는 기존 페이지와 다른 페이지의 연쇄 참조 변경까지 미리보기와 승인 해시에 포함되는지 검사한다. 기존 `test_reingest_invalidation_replay`·`test_reingest_reference_prune`·`test_reingest_ledger_lag`의 동작을 재사용한다. 승인 후 다른 문서의 편입·수동 편집·lint로 공개 상태 지문·영향 대상·결과가 바뀌면 반영하지 않는지, 원격 원장 지연·대기 기여 누락을 조용히 무시하지 않는지 검증한다. 미리보기 실패·중단 시 본문·operation artifact·journal·callback·캐시의 비트랜잭션 효과가 공개 상태를 바꾸지 않는지도 검사한다.
- ingest·lint 출시 전: 본문 업로드 실패, 업로드 후 DB 롤백·프로세스 종료, 커밋 후 응답 유실을 주입한다. 실패 시 기존 본문과 원장을 유지하고 성공 시 새 참조·기여·반영 상태·outbox가 함께 공개되는지 검사한다. 조회·검색·임베딩의 미공개 객체 접근, 웹 편입·수동 편집·lint·복구의 과거 객체 덮어쓰기, 정리 작업의 진행 중·복구용 객체 삭제가 없는지도 확인한다.

## Alternatives

- **ai-svc에 Python(FastMCP)으로 MCP 서버를 둔다:** 기존 내부 API에는 서비스 토큰 인증이 있지만 외부 MCP 사용자의 OAuth 인증·인가를 대신하지 못한다. 이 배치는 ai-svc에 MCP용 사용자 인증·access 권한 조회 경계를 추가해야 하고, 기존 내부 API가 외부에 노출되지 않도록 라우팅도 분리해야 한다. 승인 API가 MCP와 같은 프로세스에 놓이는 점도 고려한다.
- **별도 mcp-svc 신설:** 배포 단위가 늘고 인가를 document-svc에 다시 물어야 한다. tool 대부분이 document-svc의 기존 client와 서비스 메서드를 감싸는 수준이라 이득이 작다.
- **개인 액세스 토큰(PAT)·고정 헤더 토큰:** 사용자별 PAT는 사용자를 식별할 수 있다. 반면 Claude 앱의 조직 공용 고정 헤더는 개인별 식별에 맞지 않는다. PAT를 제외하는 이유는 식별 불가능이 아니라 Claude 원격 연결 호환성과 동의·회수 경험의 통일, 인증 경로 추가를 피하기 위해서다.
- **Dynamic Client Registration:** 2026-07-28 사양에서 deprecated 됐다. 연결마다 클라이언트가 새로 등록돼 쌓이고, 아무 클라이언트나 받게 된다. CIMD와 허용 목록을 쓴다.
- **2026-07-28 사양과 Java SDK 2.2.0 정식판을 기다린다:** Claude가 따르는 사양이 2025-11-25이고, 2.2.0은 아직 마일스톤이다. 기다릴 이득이 없다.
- **sampling으로 서버 파이프라인의 LLM 호출을 클라이언트에 위임:** 사양에서 deprecated 됐고, LLM 호출 경로마다 위임 분기가 필요하다.
- **MCP ingest를 Kafka worker로 실행:** worker는 서버 LLM 실행기다. MCP 경로의 실행 주체는 클라이언트 모델이고, 서버는 상태 저장과 검증만 한다.
- **window 결과를 위키에 즉시 반영:** 끊긴 run이 공유 위키를 일부만 바뀐 상태로 남긴다.
- **ingest를 서버 검증만으로 반영(승인 없음):** 원문에 실제로 있는 문장을 골라 엮는 왜곡은 결정적 검증으로 잡을 수 없다. 공유 위키는 다른 멤버의 서버 Agent·Query와 MCP 클라이언트가 읽으므로 저장형 인젝션이 workspace 전체로 퍼진다.
- **ingest를 MCP에서 뺀다:** 가장 안전하지만, 사용자 모델로 편입한다는 목적의 핵심을 버린다. 네 겹 방어로 위험을 줄이고 유지한다.
- **결과물을 자유 Markdown으로 받는다:** 숨은 지시·외부 링크·원문 밖 내용을 검사할 기준이 약하다. 기존 concept 재조립 구조와도 맞지 않는다.
- **tool 호출당 과금:** 조회 tool이 잘게 여러 번 불려서 사용자가 비용을 예측하기 어렵다.
- **성공 결과가 하나라도 남으면 계획 정액 청구:** 20개 중 1개만 성공해도 전액을 받으므로 사용자 관점에서 불공정하고, 미완료 복구와 완료 후 복구의 환불 비대칭도 설명하기 어렵다. 성공한 승인 변경 건당 고정 단가와 계획당 상한을 채택한다. `계획 정액 × 성공/승인 비율`도 실패 작업으로 분모를 부풀릴 수 있어 기각한다.
- **초기 건별 수수료 없이 요금제·사용 한도로 운영:** 플랫폼 수수료 원장·예약·정산/환불을 초기 범위에서 뺄 수 있지만, 성공한 변경에 수수료를 받는 A안을 선택했으므로 이번에는 채택하지 않는다. 이 대안을 채택해도 사용자 권한·중복 실행 방지·작업 이력·관리자 중단과 별도 서버 모델 비용 관리는 유지한다.
- **승인 범위가 전부 성공한 경우에만 계획 수수료 청구:** 현재 부분 실패는 자동 롤백하지 않아 성공한 변경이 남는다. 실패할 작업을 끼워 넣어 나머지를 무료 실행하는 우회가 생기므로 채택하지 않는다. 실패한 작업은 무료로 두고 실제 성공한 승인 변경에만 과금한다.
- **연결 해제 시 모든 실행 자동 롤백:** 웹에서 이미 승인한 작업의 취소와 클라이언트 접근 회수는 다르다. 자동 롤백도 추가 쓰기이며 후속 편집과 충돌할 수 있다. 사용자 연결 해제는 승인된 실행을 유지하고, 관리자 차단은 다음 작업 경계에서 멈추며, 복구는 기존 웹 경로에서 별도로 선택한다.
- **서버 Agent(`/agent/turn`)를 MCP tool 하나로 노출:** 라우팅·편집안 생성이 서버 LLM으로 돌아 사용자 모델로 작업한다는 목적과 맞지 않는다. 그런 사용은 웹 경로나 BYOK([0029](0029-byok-user-llm-key.md))가 맡는다.
- **MCP 대화 안에서 승인(`approve_run` tool):** 클라이언트 모델이 스스로 호출할 수 있고, 사용자가 tool 호출을 "항상 허용"으로 두면 사람의 확인이 사라진다.
- **MCP 쓰기를 즉시 실행:** 웹 경로의 승인·충돌 검사·롤백 보장이 MCP 경로에서만 빠진다. Supabase·GitHub 사례처럼 쓰기 tool이 유출 경로가 된다.
- **팀 Skill을 MCP skills 확장(2026-09-13 확정)으로 노출:** 확장은 파일별 SHA-256 manifest로 승인 뒤 변경을 막지만, 다른 멤버가 쓴 지시가 사용자 모델에 들어가는 문제는 그대로다. **본인이 쓴 개인 Skill**은 이 문제가 없으므로 이후 선택지로 남긴다.
- **MCP Apps로 대화 안에서 diff를 보여 주고 승인:** 미리보기는 "두 화면 오가기"를 줄이는 선택지로 남긴다. 다만 UI에서 하는 작업도 tool 호출 경로를 타므로 승인은 계속 웹앱에서만 받는다.
- **서비스 권한으로 tool 실행 후 결과 필터링:** GitHub PAT·Supabase `service_role` 사례처럼 필터 누락 한 번이 전체 유출이 된다. 사용자 권한으로 조회하는 방식이 실패해도 피해 범위가 좁다.

## Consequences

- 사용자는 Claude 커넥터에 URL을 등록하고 OAuth로 로그인한 뒤, 대화로 질문·편입·정리·편집을 요청한다. 결과는 웹앱과 같은 곳에 쌓인다.
- MCP를 열기 전에 access에 인가 서버 층을 만들어야 한다. 출시 범위가 읽기 전용이어도 이 작업과 교차 tenant·토큰 계약 테스트, 감사 로그, 연결 회수 UI는 줄지 않는다.
- 문서 편집·변경과 위키 반영은 MCP 대화에서 제안하고 웹앱에서 승인하므로, 사용자가 두 화면을 오가야 한다. 편입 미리보기 화면이 새로 필요하다(frontend 이슈로 계약 전달).
- 편집 품질 평가 LLM이 빠지므로, MCP 편집안의 품질은 클라이언트 모델과 사용자 검토에 달린다.
- 운영 호출자가 없던 `POST /internal/agent/runs/artifacts/register`를 MCP 편집 제안이 사용한다. LLM 플래너 없이 계획을 만드는 내부 API가 추가되고, MCP run은 revise를 막는다.
- MCP 제안은 기존 사용자 자동 승인 설정에서 제외되므로 웹 제안과 승인 동작이 다르다. 출처를 저장·전달하는 계약과 양쪽 승인 API의 차단이 필요하다.
- 위키의 원자적 공개를 위해 웹 편입(수동 및 업로드/변환 후 자동 편입)·수동 편집·lint·복구도 변경 불가능한 본문 객체와 DB 참조 방식으로 전환한다. 기존 S3 저장 함수를 그대로 재사용하는 작업으로 산정하지 않으며, 미공개 객체 정리와 복구용 객체 보존·파기까지 4단계 범위에 포함한다.
- 위키 품질이 사용자 모델에 따라 달라질 수 있다. 구조화 기여·원문 대조·승인이 공유 위키 품질의 최소선이다. 애매한 개념 병합은 하지 않으므로 MCP 편입 뒤 개념 중복이 늘 수 있고 lint가 정리한다.
- 큰 문서 편입은 사용자 모델의 사용 한도를 많이 소모한다. 대량 편입은 웹 경로(서버 LLM 또는 BYOK)가 계속 주 경로가 된다.
- access에는 grant·연결 회수 계약, document-svc에는 MCP·승인 UI 계약·수수료 원장, ai-svc에는 공통 검증·조회 전용 API·MCP run/draft/멱등/스냅샷·결과 outbox 계약이 추가된다. MCP 승인 API는 document가 전달한 안정된 approval ID를 받아 같은 ID의 재시도를 멱등 처리하고, 취소된 ID의 지연 승인·enqueue를 거절하도록 확장한다. 구현 시 각 저장소의 `docs/api/`·데이터 모델·마이그레이션·파기 계약·테스트를 함께 갱신한다. 기존 모델 `/usage`를 플랫폼 수수료 원장으로 확장하지 않는다.
- 부분 실패·취소·관리자 중단 시에도 실제 성공한 승인 변경 건수만큼 청구하며 계획당 상한을 적용한다. 이후 복구해도 성공 변경 수수료는 환불하지 않는다. 승인 화면과 이력에 이를 명시해야 한다. 결과 불명확 상태의 대사가 필요하고, 사용자 연결 해제는 이미 웹 승인한 작업의 취소가 아니다.
- 원문 조회와 위키 반영은 분산 트랜잭션이 아니다. 마지막 조회 이후 원문 변경은 편집 이벤트와 stale 표시로 수렴하며, 반영 시점의 절대 최신성을 보장하지 않는다.
- grant·정책 및 현재 멤버십·권한을 매번 원본 저장소로 확인하므로 access의 가용성과 지연이 MCP 호출에 직접 영향을 준다. access에서 확인할 수 없으면 읽기까지 차단하며, 이미 승인된 실행도 새 변경 경계에서 현재 권한·차단 상태를 확인할 수 없으면 진행하지 않는다. 기존 권한 캐시가 남아 있어도 대체 근거로 사용하지 않는다.
- MCP 사양을 2025-11-25로 시작하므로, 클라이언트가 2026-07-28로 옮겨 가면 SDK 업그레이드와 stateless 전환 작업이 따로 생긴다.
- 사용자 클라이언트의 다른 커넥터를 통한 유출은 남는 위험이다. 관리자 허용과 고지로 책임 범위를 명확히 한다.
- **전제:** 위키가 하나의 공유 인덱스로 성립하는 것은 멤버 전원이 모든 문서를 읽을 수 있기 때문이다. 문서 단위 읽기 제한이 생기면 MCP 이전에 위키 구조(검색·개념 합성)부터 다시 설계해야 한다.
- 미결 사항:
  - access에 Spring Authorization Server를 도입할지, 기존 JWT 발급 코드에 MCP 토큰 층을 직접 얹을지(access 담당자)
  - Claude 웹 앱이 쓰는 CIMD URL 확인, Anthropic-held client credentials(`oauth_anthropic_creds`)로 디렉터리에 등록할지
  - 원문 대조의 어휘 겹침 기준값과 지시형 문장 패턴(평가셋으로 정한다)
  - 출시 전 외부 보안 점검(침투 테스트) 범위
  - 성공 변경 건당 단가와 계획당 상한 값, 읽기 tool의 요금제 포함 여부와 일일 한도(백엔드·사업; A안과 복구 시 무환불 원칙은 결정됨); 편입의 고정 원문 분량 산정 단위·가격 구간 또는 산식과 lint 반영 단가(4단계 출시 조건)
  - document 실행 영수증·수수료 원장과 ai 위키 결과 이벤트의 구체 스키마·전달/대사 계약, 정산 보류의 예약·조정 처리 기한(원장 분리와 소유권은 결정됨)
  - draft·미리보기·멱등 기록 만료 시간, 사용자·workspace별 활성 개수와 저장량 상한, 감사·정산 기록의 파기/보존 및 미확정 건의 기한 만료·보존 불가 시 처리 계약(수수료 관련 항목은 2단계 출시 조건)

### 구현 시 빠뜨리지 않을 연결 지점

- **제안 생성:** `create_with_planning_job`을 그대로 호출하면 서버 플래너 작업이 생성된다. 기존 저장 로직은 재사용하되 MCP의 검증 완료 계획·artifact·출처 저장을 원자적으로 수락하는 경로를 분리한다. 내부 메서드를 재사용할 수 있는 곳에서 자기 서비스 HTTP API를 다시 호출하는 계층은 추가하지 않는다.
- **승인·권한:** `AgentTurnService.getRun`과 plan-ready 경로뿐 아니라 ai 승인 API도 자동 승인 요청을 차단한다. `DocumentAccessPolicy`의 OWNER 예외가 캐시된 역할을 다시 읽지 않도록 현재 판정 문맥을 실제 변경 서비스까지 전달한다. 웹의 기존 캐시 정책은 유지한다.
- **실행·정산:** approval ID는 document가 정하고 ai는 같은 ID의 재시도를 멱등 처리한다. `prepareToolApply`와 24시간 응답 캐시는 영수증을 대신하지 않는다. 예약 타입을 구분해 `releaseStale`·모델 사용량 정산이 MCP 예약을 해제하거나 청구하지 않게 한다. 종료 상태·복구 상태와 정산 상태를 분리한다.
- **개념 매핑:** `normalize`, `NameMatchConceptResolver`/`_exact_name_match`, `merge_concept_ledger`, `_core_concept_promotions`, 승격 영속화 및 `postgres_wiki_writer`를 하나의 변경 범위로 추적한다. slug 유래 별칭을 제거하는 일과 제목·진짜 별칭을 보존하는 일을 구분한다. 과거 데이터의 자동 병합 해제는 만들지 않는다.
- **위키 공개:** `_rebuild_invalidated_pages`·`_prune_dangling_references`와 기여 재생 규칙을 미리보기/반영이 공유한다. 기존 journal 복구가 고정 객체를 덮어쓰는 우회 경로로 남지 않게 한다. 상태 테이블만 옮기고 S3·callback·캐시의 부수 효과를 놓치지 않는다.
- **수명주기:** schema·인덱스·유일 제약뿐 아니라 purge, TTL 정리, outbox 재시도, 만료 artifact, 상태 조회와 프런트엔드 상태 매핑을 같은 작업의 체크리스트에 넣는다. 파기된 scope의 지연 작업은 재생성하지 않는다.

### 단계별 출시 게이트

1. **읽기:** I0~I3 완료. 인가 서버 선택·허용 클라이언트·읽기 한도 확정과 실제 연결 검증이 필요하다. 쓰기 도구는 노출하지 않는다.
2. **문서 편집:** I4~I5 완료. 단가·상한, 안정된 승인/영수증 계약, 미확정 예약 처리 기한, 감사·정산 보존/파기 정책을 확정한다. 웹 조회 없이도 정산이 끝나야 한다.
3. **다단계 변경:** I6 완료. 부분 승인·부분 실패·예산 소진·미확정 생성의 검증을 통과해야 한다.
4. **편입·lint:** I7~I9 완료. 원문 분량 산정·가격과 검증 휴리스틱을 확정하고, 공통 저장 경로 전환 및 실패 주입 검증을 먼저 완료한다. MCP draft 미리보기만 완성됐다는 이유로 공개하지 않는다.

### 배포와 검증 방법

- 각 단계는 DB의 추가 스키마와 읽기 호환을 먼저 배포하고, 공급 서비스의 새 계약이 준비된 뒤 소비 서비스와 UI를 연결한다. 불변 본문으로 전환한 뒤에는 고정 객체 덮어쓰기를 재개하는 구버전 writer로 되돌리지 않는다. 문제 발생 시 새 실행을 중단하고 기존 공개 참조·복구 이력을 보존한 채 수정한다.
- workspace 허용을 켜기 전 각 단계의 계약 테스트를 수행한다. 읽기·편집·계획·편입/lint를 순차 공개하며, 장애 시 회수/관리자 차단은 본문의 실행 경계와 정산 규칙을 따른다. 단순 도구 비노출을 이미 승인된 실행 중단의 대체 수단으로 쓰지 않는다.
- 수정자는 해당 변경의 단위·계약·DB 통합 테스트를 실행하고, 리뷰어는 변경과 전파 범위 및 빠진 검증만 확인한다. 저장소 전체 검사는 최종 통합 시 한 번 수행하고, 실패나 새 변경이 있을 때만 관련 검사를 반복한다.
- DB·객체 저장소·원격 서비스 실패 주입 및 실제 OAuth 연결은 정적 검토로 대체하지 않는다. 현재 이 문서에는 테스트 실행 성공을 기록하지 않았다.
