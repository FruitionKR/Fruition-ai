# 0045. 라우팅은 1차에서 큰 작업만 고르고, 세부는 작업별 2차에서 한 번에 고른다

## Status
Proposed

## 맥락
ADR-0010은 Markdown 요청을 하나의 Agent Turn이 분류한다고 정했고, ADR-0043은 그 위에 편집 세부 분류를 더했다. 작업이 늘면서 판단 단계가 구조 없이 쌓였다.

- **편집은 Jev 기준 판단이 3단계다.** 작업 종류를 고르고(`route_options`), 편집 목표·방식·위치 조합을 고르고(`edit_options`), 편집기 안에서 세부 분류를 한다(`ChatCompletionsMarkdownEditor.generate_edit`). LLM 라우터는 앞의 둘을 한 번에 고른다.
- **같은 판단이 두 곳에 찢어져 있다.** 글머리표·체크리스트는 라우터의 `edit_goal`이, 번호 목록·표는 세부 분류의 `requested_formats`가 정한다. 번역도 `edit_goal=translate`와 `target_language`로 나뉜다.
- **두 단계가 서로 모른다.** ADR-0043 결정 2로 세부 분류에 `edit_goal`을 넘기지 않는다. "제34조를 유출 사고 대응 체크리스트로 바꿔줘"를 세부 분류가 번호 목록으로 골라, 체크리스트 목표 검사와 충돌해 3회 모두 실패했다(2026-11-05). 체크리스트 자리(`other_list`)를 더해 막았지만, 이 자리는 "내 일이 아니다"라고 답하는 임시 칸이다.
- **1차 선택지가 무겁다.** 작업 종류·검색 위치·문서 작업·능력 조합이 측정한 조건에서 48~126개이고, 절반 안팎이 `workspace_workflow` 조합이다. Jev 한도는 255개(`MAX_CHOICES`)다. 큰 작업과 세부를 한 번에 보는 탓에, "열린 문서 요약본을 따로 하나 만들어줘"를 작업 탭 Jev가 3회 모두 편집으로 골랐다(2026-11-05, 5문장 3회 측정, LLM은 생성).
- **작업마다 2차 유무가 다르다.** 폴더 지목과 Skill 의도, 근거 선택은 이미 작업별 Jev 판단이다. 생성은 2차가 없어, 원문은 코드가 정하고 열린 문서를 쓸지는 생성 LLM이 정한다.
- **문서와 실제가 다르다.** 라우터 프롬프트는 "실행기는 재분류하지 않는다"고 쓰지만, 세부 분류기와 폴더 플래너, 편집 프롬프트의 `other` 추론은 다시 판단한다.

## 결정
모든 작업을 **1차(큰 작업) → 2차(작업별 세부)** 로 나눈다. 판단은 Jev가 먼저 하고, 실패하면 같은 구조의 LLM이 한다(ADR-0027).

1. **1차는 큰 작업만 고른다.** 편집, 생성, 폴더 정리, 폴더 조회, 대화·질문, 워크스페이스 활용, Skill 작성·초안, 되묻기, 거절과 Skill 선택·안내 종류다. 검색 위치, 문서 작업, 능력, 편집 필드는 2차로 옮긴다.
2. **2차는 작업별로 둔다.**

   | 작업 | 2차에서 고르는 것 |
   |---|---|
   | 편집 | 무엇을 하나(한 질문), 방식, 위치, 추가 여부, 구조 변경, 번역 언어, 검색 위치 |
   | 생성 | 결과 형식, 참고 대상(없음, 대화, 열린 문서, 폴더), 검색 위치 |
   | 대화·질문 | 검색 위치 |
   | 워크스페이스 활용 | 필요한 능력, 문서 작업, 검색 위치 |
   | 폴더 조회, Skill 작성 | 지금 판단 유지 |

3. **편집의 "무엇을 하나"는 한 질문의 보기로 둔다.** 체크리스트, 글머리표, 번호 목록, 표, 인용, 제목, 수식, Mermaid, 코드 블록, 회의록, 강조, 줄이기, 문체, 정리, 번역, 기타다. 보기가 나란히 있으므로 목표와 형식이 어긋나지 않고 `other_list`가 필요 없다. 양식 변환(`template_transform`)은 코드 분기가 clarify 문구뿐이고 평가 정답에도 0건이라, 보기로 둘지 구현 때 다시 본다.
4. **2차는 라우터 안에서 라우트를 완성한다.** clarify 문구와 `insert_after` 판정(`handle_agent_turn`)이 편집 필드를 쓰므로 실행 전에 값이 있어야 한다. 라우터를 거치지 않는 경로(`/slug` 단독 실행, Skill 시험 실행)는 같은 2차 부품을 직접 부른다.
5. **출력 필드는 이름과 값을 유지한다.** 편집 보기는 기존 `edit_goal`과 `requested_formats`로 바꿔 넘긴다(체크리스트 → `checklist`, 표 → `convert_format` + `table`). 그래서 검사, 편집 프롬프트, `route` 응답, 이전 턴 `agent_route` 재전송은 바뀌지 않는다.
6. **코드가 요청 문장을 해석하지 않는 원칙(ADR-0043 결정 3)은 유지한다.** `/slug`, 승인 대기 Skill의 후속 동작, 안전 검사 정규식은 의도 분류가 아니라 명령·안전 처리라 그대로 둔다.
7. **편집부터 단계적으로 옮긴다.** 단계마다 아래 기준을 넘어야 다음으로 간다. 기준을 못 넘으면 그 단계를 되돌리고 기존 구조를 유지한다.

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| 0 | 지금 구조의 1·2·3단계를 함께 돌리는 평가 도구를 만들어 기준선을 잰다 | 기준선 기록 |
| 1 | 편집: 1차에서 편집 필드를 빼고 2차로 합친다. 세부 분류 호출을 지운다 | 라우팅과 세부 분류 정확도가 기준선 이상, 실제 편집 30건 × 3회가 기준선 이상, 호출 수 감소 |
| 2 | 생성: 2차를 만들고 참고 대상을 고른다 | 생성 평가 기준을 먼저 만들어 고정한 뒤 기준선 이상 |
| 3 | 대화·질문, 워크스페이스 활용: 검색 위치와 능력을 옮긴다 | 질문·대화 라우팅 정답을 먼저 추가한 뒤 기준선 이상, 1차 선택지 감소 |

## 평가
- **잠긴 라우팅 정답은 고치지 않는다.** 결정 5로 최종 라우트 필드가 같으므로 `routing.jsonl` 102건의 기대 답을 그대로 채점한다. 2단계 이후 필드 위치가 바뀌어도 최종 라우트로 비교한다.
- **단계별 원인을 나눠 본다.** 최종 답이 틀리면 1차와 2차 중 어디서 틀렸는지 기록한다.
- **실패 내역을 보지 않은 사람이 새 문장을 쓴다.** 체크리스트, 글머리표, 번호 목록, 끝에 추가, 요약 새 문서, 양식 변환, 영어, 긴 요청, 대화 요약, Skill 지침을 포함한다. 가능하면 실제 로그에서 뽑는다. 문구를 고정한 뒤 판단용으로 한 번만 돌리고, 정답은 `gold.lock.json`에 고정한다.
- **프롬프트와 선택지에 평가 문장을 넣지 않는다.**
- **속도와 비용을 함께 잰다.** 단계별 호출 수, 지연, 사용량 원장 기준 비용이다.

## 0단계 기준선 (2026-11-05)
`evals/jev/tools/run_route_chain.py`로 라우터와 세부 분류를 운영 순서대로 함께 돌렸다. 잠긴 `routing.jsonl` 102건 × 3회, gpt-6-luna, 실제 편집 없음.

| | Jev | LLM |
|---|---|---|
| 라우팅 정답 | 276/306 | 282/306 |
| 틀린 문항 | 12 | 10 |
| 세부 분류까지 간 행 | 163 | 154 |
| 목표와 형식 충돌 | 0 | 2 (`convert_format`인데 형식 없음) |
| 라우터 건당 중앙값 | 0.42초 | 2.87초 |
| 세부 분류 건당 중앙값 | 0.19초 | 2.15초 |

- **체크리스트·글머리표 목표와 번호 목록의 충돌은 0건이다.** `other_list`를 더한 뒤라 이 평가셋에서는 맥락에 적은 충돌이 재현되지 않는다. 이 결정의 근거는 충돌 빈도가 아니라 구조 단순화와 호출 감소다. 충돌을 줄이는 효과로 판단하지 않는다.
- 문항 단위로 Jev가 나쁜 9, 좋은 6이라 라우팅 차이는 판별할 수 없다. 오답은 대부분 1단계(작업 종류) 오답이다. "이 문서 복사본을 만들어서 영어로 번역해줘"처럼 생성을 편집으로 고르는 오답은 Jev에만 나왔다.
- 실제 편집 기준선은 Jev·LLM 모두 82/90이다(라우터 값을 평가셋으로 고정, #217 없는 코드).

## 대안과 기각 사유
- **지금 구조를 유지하고 충돌만 막기:** 변경이 가장 작다. 다른 형식에서 같은 충돌을 반복하고 임시 칸이 남는다. 평가 기준을 넘지 못하면 돌아갈 자리다.
- **세부 분류에 `edit_goal`을 넘기기:** 어긋남은 줄지만 앞 단계가 틀리면 끌려간다. ADR-0043 결정 2가 피하려던 문제다.
- **1차에서 모두 한 번에 고르기:** 호출은 가장 적다. 조합이 Jev 한도를 넘고, 판단이 틀리면 전부 틀린다. ADR-0043이 기각한 방향이다.
- **문서 종류로 생성 2차를 나누기(보고서, 회의록 등):** 코드가 문서 종류로 다르게 동작하는 곳이 없어, 지금은 결과 형식과 참고 대상만 고른다. 동작이 달라지는 종류가 생기면 다시 본다.
- **모든 작업을 한 번에 옮기기:** 어디서 나빠졌는지 가릴 수 없다.

## 결과
- 편집의 판단이 3단계에서 2단계로 줄고, 목표와 형식이 어긋나는 경로가 사라진다.
- 1차 선택지가 줄어 큰 작업 판단이 쉬워질 것으로 기대한다. 단, 편집과 생성을 가르는 오분류가 줄어드는지는 재 봐야 한다.
- 모든 문서 작업과 질문에서 2차 호출이 1회 생길 수 있다. Jev 비용과 지연이 늘 수 있어 단계마다 잰다. 대화처럼 고를 값이 없는 경우는 호출하지 않는다.
- Jev 2차가 실패하면 LLM으로 넘어가며 그만큼 지연이 는다. 요청 마감은 Jev 호출에 이미 반영했다.
- 이 결정이 Accepted가 되면 ADR-0010, ADR-0027, ADR-0043의 해당 부분을 개정하고, 라우터 프롬프트의 재분류 문구를 실제에 맞춘다.

## 구현 전에 확인할 것
- document-svc와 frontend 최신 코드가 `route`의 편집 필드를 읽는지. 지금까지는 로컬 체크아웃에서 이름으로만 찾았고, document-svc는 `route`를 통째로 전달하는 것으로 보인다.
- 열려 있는 #222(Agent turn의 첨부 문서 근거와 문서별 수정 계획)와의 겹침.
- Jev 선택지 한도 255의 공급자 근거. 저장소에서 찾지 못했다.
- 대화 요약과 긴 Skill 지침이 들어올 때 2차 요청 크기. Skill 지침 약 20만 자에서 Jev가 HTTP 400을 냈고 LLM으로 넘어갔다.
