# 0044. post_ingest 단계 실패는 run을 되돌리지 않고 부분 성공으로 끝낸다

## 맥락
post_ingest 한 run은 서로 독립인 세 단계를 묶는다. 편입 페이지 임베딩, 의미 클러스터 판정·저장, 품질 평가다. 같은 프로세스 안에서 세 번까지 재시도하고 체크포인트한 단계는 다시 하지 않는다. 그런데 세 번째 시도도 실패하면 run을 실패로 끝냈고, 작업 기록부(`ai_task_changes`)가 그 run이 바꾼 행을 전부 되돌렸다.

- 한 단계의 실패가 이미 성공한 다른 단계의 결과까지 지웠다. dev DB의 실패 4건은 모두 클러스터 판정이 성공한 뒤 임베딩이 세 번 실패해 클러스터 결과까지 사라졌다. 반대로 임베딩이 성공해도 품질 평가가 끝까지 실패하면 페이지 벡터 행이 삭제됐다.
- 부모 ingest manifest에 쓴 `post_ingest.status=needs_review`와 실패 코드도 되돌려져 NULL이 됐다. `data-model.md`의 "상태를 보존한다"와 맞지 않았다.
- 페이지 벡터 행이 지워진 페이지는 임베딩 복구 대상이 아니었다. 복구는 기존 행 중 `pending`·`failed`만 골랐고 maintenance worker 기동 때만 돌았다. 그래서 그 페이지는 다시 임베딩되지 않았다(dev 활성 페이지 88개).

## 결정
1. **post_ingest의 마지막 시도가 실패해도, 취소가 아니면 run을 성공으로 끝낸다.** 성공한 단계의 결과는 남기고 부모 manifest의 `post_ingest.status`를 `needs_review`로 둔다. 결과와 부모 manifest에 `error`(실패 코드)를, 결과에 `failed_stage`(`stage_timings`에서 마지막으로 실패한 단계)를 남긴다.
2. **취소(`PipelineRunCancelledError`: 사용자 취소·마감 초과·원본 삭제·파기)는 지금처럼 실패로 끝내고 되돌린다.** 취소된 작업의 결과는 남기지 않는다.
3. **임베딩 복구는 "임베딩이 덜 된 활성 페이지"를 직접 찾는다.** 완료된 페이지 벡터가 없거나(행이 없는 경우 포함) 완료되지 않은 단위 벡터를 가진 활성 페이지가 대상이다. maintenance worker는 기동 직후와 10분마다 복구를 돌린다. 주기 복구는 다른 임베딩 작업이 advisory lock을 쥐고 있으면 기다리지 않고 건너뛴다.

## 대안과 기각 사유
- **임베딩 테이블만 작업 기록부 추적에서 빼기:** 이미 계산한 벡터는 살리지만 클러스터 결과와 실패 기록은 여전히 사라진다. 기록부 원칙에 테이블 단위 예외도 생긴다.
- **단계마다 별도 Kafka 작업·run으로 쪼개기:** 경계는 가장 명확하지만 document와의 종료 이벤트·사용 금액 정산 계약과 상태 집계를 모두 다시 짜야 한다. 지금 문제는 run 안에서 실패를 되돌리지 않는 것으로 해결된다.
- **복구 대상만 넓히고 기동 때만 돌리기:** 다음 재시작 전까지 그 페이지는 의미 검색에서 빠진다.

## 결과
- document는 post_ingest가 끝까지 실패해도 실패 대신 완료 이벤트(`quality_status=needs_review`)를 받는다. document는 post_ingest 종료 이벤트를 상태와 상관없이 사용 금액 정산과 ingest 예약 해제에만 쓰므로(`AiTaskResultApplier.applyPostIngest`) 계약은 바뀌지 않는다.
- 임베딩이 실패한 페이지는 `failed`·`pending` 행으로 남고 주기 복구가 다시 처리한다. 원본 markdown을 읽을 수 없는 페이지처럼 계속 실패하는 페이지는 10분마다 다시 시도되고 오류 로그를 남긴다.
- 진행 중인 post_ingest의 페이지를 주기 복구가 함께 임베딩할 수 있다. 쓰기는 `updated_at`이 같을 때만 반영되므로 결과는 같고 계산만 한 번 겹친다.
