# 0033. 위키는 워크스페이스 공유 자산으로 저장하고, 편입은 권한을 받은 멤버가 수동으로 한다

## Status
Accepted

## Context
위키는 팀이 함께 쓰는 지식 저장소다. 그런데 지금은 읽기와 쓰기의 단위가 서로 다르다(Fruition-ai#73).

| 영역 | 현재 단위 | 결과 |
|---|---|---|
| 질의 검색·그래프·페이지 조회 | 워크스페이스 | 멤버 A가 만든 위키를 멤버 B도 질의에 쓴다 |
| 페이지 저장 키 `UNIQUE (user_id, workspace_id, page_type, slug)` | 사용자 | 두 멤버가 같은 문서·개념을 편입하면 페이지가 두 벌 생겨 검색 결과와 그래프에 중복으로 나온다 |
| 개념 병합(`canonical_slug`) | 사용자 | 같은 개념이 사용자 사이에서는 합쳐지지 않는다 |
| 저장 보조 잠금 `concept-persistence:{user_id}:{workspace_id}`, Redis 개념 목록 캐시 | 사용자 | 공유 저장으로 바꾸면 범위가 맞지 않는다. 반영 단계의 주 잠금(`concept_write_lock`)은 이미 워크스페이스 단위다 |
| S3 키 `wiki/{user_id}/{workspace_id}/sources·concepts·clusters·logs/` | 사용자 | 페이지 이력(`wiki/{workspace_id}/pages/{id}/ops/`)만 워크스페이스 단위라 키 구조가 섞여 있다. 파기는 `wiki/`를 나열해 사용자 prefix를 찾는다(ADR 0029) |
| 이름 변경 | 작성자만 | 다른 멤버가 바꾸면 404가 났다. 공개 API는 Fruition-document B5a에서 닫았다 |
| 문서 삭제 정리 | 사용자 취소·문서 전체 판정 | ADR 0032에서 워크스페이스 단위의 비동기 정리로 바꿨다 |

권한은 access의 `WorkspaceRole`(OWNER·MEMBER) 두 단계뿐이다. 편입처럼 공유 위키를 바꾸는 행동을 멤버별로 허용하거나 막을 수 없다. PDF를 올리면 변환이 끝나는 대로 업로더 이름으로 자동 편입한다(`DocumentService.doConvertBatches`). 그래서 문서를 올리는 일과 팀 위키에 넣는 일이 분리되지 않는다.

## Decision
1. **소유 단위**
   - 위키(페이지, 문서-페이지 연결, 임베딩, 원문 조각)와 AI 작업 실행 기록은 워크스페이스 자산이다.
   - 채팅 세션은 개인 자산이다.
   - `user_id`는 키에서 빼고, 누가 편입을 요청했는지 남기는 귀속 정보로만 둔다.
2. **저장**
   - 페이지 고유 키를 `(workspace_id, page_type, slug)`로 바꾼다.
   - 소스 페이지는 문서당 하나다. slug가 `document_id`라서, 같은 문서를 누가 다시 편입하든 같은 페이지를 갱신한다.
   - 개념 페이지는 워크스페이스 안에서 기존 병합 규칙(`canonical_slug`)으로 합친다.
   - **소스 페이지 제목은 문서 파일명이다.** 지금은 편입 결과의 제목이나 본문의 첫 제목을 쓴다. 그래서 파일명이 달라도 본문 제목이 같으면 위키 제목이 겹친다.
     - document 이름은 같은 폴더 안에서만 유일하다(Fruition-document `V51`, `uq_document_tree_active_name`). 그래서 다른 폴더의 같은 파일명은 "파일명 · 폴더 경로"로 구분한다. 폴더와 파일명을 함께 보면 항상 유일하다.
     - ai는 편입을 실행할 때 document `pipeline-source`의 파일명에서 확장자를 뗀 이름을 소스 페이지 제목으로 저장한다(ingest command의 `display_name`은 선택 필드이며 document는 보내지 않는다). 질의 답변의 근거 표시도 이 제목을 쓴다. 채팅 내보내기 문서는 생성 제목을 그대로 쓴다.
     - document가 문서 이름을 바꿀 때 `document_renamed` command(`title`=새 표시 이름)를 보내고, ai가 소스 페이지 제목을 바꾼다. 다시 편입하지 않아도 되고 위키 데이터의 소유는 ai에 남는다. 폴더 이동·폴더 이름 변경은 문서 표시 이름을 바꾸지 않으므로 보내지 않는다. 같은 이름의 문서를 폴더 경로로 구분하는 일은 화면이 한다(Fruition-frontend#150).
     - 개념 페이지는 병합되므로 제목이 겹치지 않는다.
3. **잠금과 캐시**
   - 저장 보조 잠금과 Redis 개념 목록 캐시를 워크스페이스 키로 바꾼다.
   - 편입의 무거운 단계(LLM 추출)는 지금처럼 잠금 없이 병렬로 돈다. 반영 단계만 워크스페이스 안에서 한 번에 하나씩 한다.
4. **S3 키**
   - `wiki/{workspace_id}/sources|concepts|clusters|logs/...`로 통일한다. 페이지 이력 키(`wiki/{workspace_id}/pages/...`)와 같은 뿌리다.
   - 이전이 끝나면 워크스페이스 파기는 `wiki/{workspace_id}/` 하나만 지운다. `wiki/` 나열 코드는 삭제한다(ADR 0029 개정).
5. **기존 데이터는 이전하지 않는다**(2026-10-11 개정).
   - 지금은 개발자 테스트 단계라, 다른 문제를 모두 고친 뒤 DB를 한 번 초기화한다. 그래서 사용자별로 쌓인 위키를 옮기는 이전 스크립트는 만들지 않는다.
   - 공유 저장으로 바꾸는 코드는 위키 데이터가 빈 상태에서 배포한다. 사용자별 중복 행이 남아 있으면 새 고유 키를 만들 수 없으므로, 기동할 때 이를 확인하고 바로 실패한다.
   - 옛 고유 키 `(user_id, workspace_id, page_type, slug)`와 사용자 prefix를 찾던 파기 코드는 같은 변경에서 지운다.
6. **권한(access)**
   - 멤버별 권한 항목을 둔다. 첫 항목은 `wiki.ingest`(위키 편입)다.
   - 권한 항목은 `wiki.ingest`(편입), `wiki.lint`(위키 정리), `skill.author`(스킬 작성·게시), `wiki.restore`(남이 실행한 작업 되돌리기), `document.convert`(남이 올린 PDF 변환)다. 구현과 결정 기록은 Fruition-access ADR 0019를 따른다.
   - OWNER는 항상 모든 권한을 가진다. 새로 초대된 멤버는 기본으로 권한이 없다.
   - 출시 전이므로 이미 있는 멤버를 포함해 모두가 권한 항목 없이 시작하고, 배포 시점에 권한을 자동으로 켜 주지 않는다. OWNER가 필요한 멤버에게 부여한다.
   - OWNER가 멤버의 권한을 켜고 끈다.
   - 되돌리기 어려운 위키 작업(페이지 삭제, 이후 다시 열 경우의 스키마 활성화)은 OWNER만 한다.
   - 다른 멤버의 진행 중 작업은 요청자와 OWNER만 취소한다.
   - 작업 로그의 복구(되돌리기)도 그 작업을 한 본인과 OWNER만 한다. 지금은 멤버 누구나 할 수 있다(`RestorePreviewService`는 `requireMember`만 본다).
   - 실행 기록은 멤버 모두가 조회한다. document의 작업 로그는 이미 워크스페이스 단위로 조회된다. 사용자로 걸러지는 것은 ai의 작업 상태·취소 API(`/tasks/{id}`)뿐이다.
7. **편입 정책(document)**
   - 업로드·변환 뒤 자동 편입을 기본값에서 뺀다. 편입은 `wiki.ingest` 권한이 있는 멤버가 수동으로 한다.
   - 워크스페이스 설정 `auto_ingest_on_upload`(access, OWNER가 변경, 기본 꺼짐)를 켜면 업로드 뒤 자동으로 편입한다. 단, 업로더에게 `wiki.ingest` 권한이 있을 때만이다.
   - 편입하지 않은 문서는 "위키 미반영"으로 표시한다. 편입 비용은 지금처럼 요청자에게 귀속한다.
8. **사용자 파기**: 이미 공용 위키를 남기고 개인 데이터(작업 기록, 에이전트 기록, 개인 스킬)만 지운다. 이 동작을 유지한다.
9. **이름 변경을 다시 열 경우**: 소스 페이지는 원문 문서의 소유자와 OWNER, 개념 페이지는 OWNER만 바꾼다.

## Alternatives
- **사용자별 저장을 유지하고 조회만 공유(현재)**: 같은 개념과 문서가 사람 수만큼 중복된다. 질의 근거와 그래프가 흩어지고, 이름 변경·삭제의 주인이 모호하다. 기각.
- **역할 추가(OWNER / EDITOR / MEMBER)**: 화면은 단순하다. 하지만 권한이 늘 때마다(편입, 페이지 이름 변경, 결제 관리 등) 역할 조합이 늘어난다. 기각.
- **업로드하면 항상 자동 편입하고, 권한은 수동 편입에만 적용**: 권한이 없는 멤버의 문서도 팀 위키에 들어가 권한이 의미를 잃는다. 기각.
- **업로드 자체를 권한으로 막기**: 문서 저장소로 쓰는 것까지 막는다. 기각.
- **멱등 이전 스크립트로 기존 위키를 옮기기**: 운영 데이터가 있다면 필요하다. 하지만 중복 병합, S3 이동, 참조 대응표, 페이지 이력 복사가 필요해 가장 복잡하고 위험하다. 개발 단계에서 DB를 초기화하므로 만들지 않는다(개정 전에는 채택안이었다).
- **제목이 같은 소스 페이지를 병합**: 서로 다른 문서의 근거가 섞인다. 기각.
- **본문 제목을 유지하고 겹칠 때만 번호나 날짜를 붙이기**: 사용자는 문서를 파일명으로 기억하는데 위키 제목은 본문에서 오므로 찾기 어렵다. 번호는 문서를 지우면 바뀐다. 기각.

## Consequences
- 같은 워크스페이스의 편입 반영 단계는 직렬로 돈다. 주 잠금이 이미 워크스페이스 단위라 지금보다 느려지지 않는다.
- 단계별로 쌓아 배포한다. 각 단계는 앞 단계 위에서 따로 동작한다.
  1. **ai**: 공유 저장, 잠금·캐시·S3 키 변경, 옛 고유 키와 사용자 prefix 파기 코드 삭제, ADR 0029의 S3 부분 개정. 위키 데이터가 빈 DB에 배포한다.
  2. **access**: 멤버 권한 항목과 `auto_ingest_on_upload` 설정 API
  3. **document**: 자동 편입 정책, 수동 편입 권한 검사, 미반영 표시, 작업 취소·조회 범위
  4. **frontend**: 문서별 편입 버튼과 미반영 표시, 관리자 설정의 권한·자동 편입 토글
- 출시 전이라 기존 멤버에게도 권한을 켜 주지 않으므로, 3단계가 나가면 OWNER가 부여하기 전까지 OWNER 외에는 수동 편입도 할 수 없다.
- 2~3단계가 배포되기 전까지는 지금처럼 업로드하면 자동으로 편입된다. 1단계만으로도 중복은 사라진다.
- 3단계가 나가면 업로드한 문서가 바로 위키에 생기지 않는다. 수동 편입 UI(그래프의 편입·최신화, 채팅 근거 안내의 편입 버튼)는 이미 있어 3단계만으로도 동작한다. 4단계는 "위키 미반영" 표시와 관리자 설정 토글을 더하는 것이므로 3단계와 함께 내보내는 것이 좋지만 필수는 아니다.
- 위키 스키마는 공개 진입로를 닫은 상태로 둔다. 다시 연다면 워크스페이스 규칙으로 바꿀지 그때 정한다.
