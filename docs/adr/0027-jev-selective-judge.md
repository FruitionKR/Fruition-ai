# 0027. 라우팅·근거 선택·개념 병합에 Jev를 선택적 판단기로 둔다

## Status
Accepted

## Context
TypeSafe Jev(`jev-1.13.0`)는 이미 추린 선택지 중 하나를 고르는 choice 모델이다. local-pilot에서 기존 경로와 비교 평가했다(원본: local-pilot `output/reports/`).

- **라우팅:** 같은 유효 route 조합에서 고르게 했다. 정확도는 Jev 81/98, 현재 JSON 라우터 77/98이었다. 중앙 지연은 0.66초와 9초였다. clarify 정확도는 Jev 0%(현재 50%)였다. holdout 재평가는 크레딧 소진(HTTP 402)으로 끝내지 못했다.
- **RAG 근거 선택:** 기존 검색으로 고른 300개 후보에서 고르게 했다. 근거 충족은 74–75/80, 기존은 52–53/80이었다. 답할 수 없는 질문 20개에서는 근거를 하나도 고르지 않았다. 비용은 질문 100개에 약 $1.39였다.
- **개념 병합:** 요청 하나에 판정 하나, 후보 3개 + `keep_new` 조건에서 GPT-5-nano 71/76, Jev 72/76이었다. 비용은 약 1/15이었다. 오류는 모두 정의 없이 이름만으로 병합한 사례였다. 이 결과는 '후보 3개 + `keep_new`' 평가 조건의 것이고, 운영 판정은 2026-10-29에 후보별 쌍 판정으로 바꿨다(아래 결정, ADR-0038). 바꾼 방식의 정확도는 아직 평가하지 않았다.

크레딧 예산이 아직 없고, AWS Secrets Manager에 키를 올린 뒤에 켤 계획이다.

## Decision
- 세 경로마다 Jev 구현을 추가하고 기존 구현을 대체 경로로 둔다. 설정은 `JEV_ROUTING_ENABLED`, `JEV_EVIDENCE_ENABLED`, `JEV_CONCEPT_MERGE_ENABLED`(기본 `false`)이다.
- 설정이 꺼져 있거나 `TYPESAFE_API_KEY`가 비어 있으면 기존 경로만 쓴다.
- 호출 실패(전송 오류, 재시도 후 429·5xx, 계약과 다른 응답)는 기존 경로로 처리한다.
- 402·401·403은 재시도로 풀리지 않는다. 프로세스 안에서 `JEV_BLOCK_SECONDS`(기본 600초) 동안 Jev 호출을 건너뛴다.
- 공통 클라이언트(`app/core/jev_client.py`)의 동작:
  - 요청 상태의 숫자 개인정보를 가리고, 보안 경계는 요청 state(JSON 객체)의 `security_boundary`에 한 번만 넣는다. 질문마다 붙이면 후보 수만큼 반복돼 요청 토큰 대부분을 차지했다. 평가셋과 다른 인젝션 사례(개념 쌍 판정 20건, 근거 선택 10건, 각 3회)에서 질문마다 붙일 때와 한 번만 넣을 때 모두 인젝션을 한 번도 따르지 않았다(2026-10-29).
  - 사용량 원장에 provider `typesafe`로 기록한다.
- **라우팅:** 기존 route 계약을 통과하는 조합에서 고르고, 편집이면 편집 목표·방식·위치를 한 번 더 고른다. 평가(`PairedChoiceClient`)와 같이 선택지를 요청 상태로 정한 고정 무작위 순서로 섞고, 기존 라우터와 같은 상태 JSON을 보낸다.
  - clarify는 선택지에서 뺀다.
  - Skill 후보의 capability가 겹쳐 clarify가 필요할 수 있는 요청은 기존 라우터가 처리한다.
- **근거 선택:** 평가한 300후보 구성(local-pilot `run_jev_300_parallel.py`)을 따르고, 병렬 수는 병렬 수 비교(local-pilot `output/jev-generalization/concurrency-2026-10-09/summary.md`) 결과에 따라 8로 둔다.
  - workspace embedding unit을 (본문, block ref, 문서)로 묶고, 기존 하이브리드 점수(BGE-M3 0.75 + BM25 0.25)로 상위 300개를 추린다. 순위 단서가 없도록 섞어서 보낸다.
  - 후보 필드는 평가와 같다(`id, text, source_titles, page_ids, source_document_id, block_refs, unit_type, weight`). 운영 unit에 없는 PDF 쪽번호(`pages`)만 뺀다.
  - 요청 본문을 cl100k_base로 세어 28,000 토큰·80개 이하로 묶고, 최대 8개 묶음을 동시에 요청한다.
  - 병렬 수 비교(같은 100문항·300후보, 조건별 1회): 선택 시간 중앙값 4병렬 2.066초(2026-09-21), 6병렬 1.165초, 8병렬 0.945초, 10병렬 0.886초. 선택이 달라진 42문항의 블라인드 채점에서 근거 충족은 37·38·36·37/42로 차이가 실행 간 변동 범위였고, 10병렬까지 529 증가는 없었다. 8 이후 이득이 0.06초로 작고, 운영 동시 요청이 질의 작업자 수 × 병렬 수로 늘어나는 점을 고려해 8을 고른다. 공급자 동시 요청 한도는 확인하지 않았으므로 배포 후 429·529·시간 초과를 본다.
  - include 확률 순으로 `QUERY_EVIDENCE_LIMIT`(기본 8)개를 남긴다.
  - 일시 오류(429·502·503·504·529, 시간 초과)는 평가 실행기와 같이 최대 4회, 2·4·8초 간격으로 시도한다.
  - 사용자가 기다리는 Agent 라우팅·Query 근거 선택은 호출 전체를 15초(`INTERACTIVE_DEADLINE_SECONDS`) 안에 끝낸다. 시간 초과는 재시도하지 않고, 남은 예산을 넘는 재시도 대기 없이 바로 기존 경로로 간다. 요청 하나의 타임아웃도 남은 예산으로 줄인다. 평가 실행기와 같은 재시도는 ingest 개념 병합에만 쓴다.
  - 웹 근거가 섞인 질의는 기존 선택기가 처리한다.
- **개념 병합:** 들어온 개념마다 다른 incoming 개념과 기존 개념을 제목·별칭·태그·정의로 하이브리드 점수(BGE-M3 0.75 + BM25 0.25)를 매겨 상위 100개를 추리고, 후보마다 질문 하나로 `same`(같은 개념)·`related`(따로 두고 연결)·`unrelated`(무관)를 판정한다(2026-10-29 변경, 이전에는 BM25 후보 3개와 `merge:<slug>`·`link:<slug>`·`keep_new` 중 하나를 고르는 질문 하나였다). 결정 규칙과 이름 일치 병합은 ADR-0038을 따른다.
  - 판정 규칙은 요청 state에 한 번만 두고, 질문 instructions에는 판정할 후보 ID만 적는다. 후보 순서는 incoming slug로 정한 고정 무작위 순서로 섞는다. 질문은 근거 선택과 같은 방식(`app/core/jev_batches.py`)으로 요청 본문을 세어 28,000 토큰 이하로 묶고, 최대 4개 요청을 동시에 보낸다.
  - 임베딩은 임베딩 서버(`EMBEDDING_SERVICE_URL`)만 쓴다. 편입 워커에 BGE-M3를 올리지 않기 위해서다(ADR-0026). 서버 설정이 없거나 잘못됐으면 경고를 남기고 기존 LLM 병합을 쓴다. 개념 텍스트 벡터는 (모델, 텍스트 해시)로 프로세스 안에 캐시해 편입마다 기존 개념을 다시 임베딩하지 않는다. 임베딩이 실패하면 BM25만으로 고르지 않고 LLM 병합으로 처리한다.
  - '따로 두고 연결'은 뜻이 다르지만 상하위·일부·단계·방법·변형·같은 상위 개념 아래의 형제·직접 의존처럼 분명히 관련된 경우다. 결과는 `link_to` resolution이고, 개념은 새로 두면서 대상 개념과 `concept_related_to` 링크를 만든다. 대상은 다른 문서의 기존 개념일 수 있어, 그래프 탐색이 문서를 넘어 관련 개념으로 이어진다. 연결 대상이 같은 턴에 병합되면 병합된 개념으로 잇는다.
  - 대체 경로인 LLM 병합(`prompts/concept_resolution.system.md`)도 같은 `link_to`를 돌려줄 수 있다.
  - 편입 중 섹션 후보·언급이 기존·이번 문서 개념과 같은지 보는 개념 갱신 후보 판정도 같은 판정기를 쓴다(2026-10-30). 후보 이름과 근거 문장을 incoming으로, 개념의 제목·별칭·정의를 pool로 두고 `same`은 `same_concept`(근거를 개념에 붙임), `related`는 `relation_candidate`로 바꾼다. 개념 근거 목록은 판정에 넣지 않는다. Jev를 쓸 수 없으면 LLM 한 번에 판정하되, 개념은 이름·별칭·정의만 보낸다. 이전에는 기존 개념 전부를 근거 목록과 함께 보내 워크스페이스가 커질수록 요청이 끝없이 커졌다(Haiku 평가에서 7문서·개념 188개에 207k 토큰으로 입력 한도 초과).
  - 같은 근거에 함께 나온 정도의 약한 관계는 지금처럼 그래프 링크로 만들지 않고 본문 Related Concepts에만 둔다. 클러스터 후보와 개념 사이의 종류 있는 관계는 lint가 만든다.
  - 정의가 없는 개념은 보내지 않는다.
  - 병합 대상이 다시 병합되는 연쇄는 버린다.
  - missing hint가 있으면 기존 LLM 결과의 `hint_resolutions`만 쓴다.
- **Skill 의도 분류(추가):** Skill을 만들 때 지원 여부·Skill 종류·참고 방식·원문 필요 여부를 고른다. 설정은 `JEV_SKILL_INTENT_ENABLED`(기본 `false`)이고 대체 경로는 기존 LLM 분류(`prompts/skill_intent_classifier.system.md`)다. Skill 본문 작성은 계속 LLM이 한다.
  - 선택지는 분류 결과 계약(`author_skill._intent_result`)을 통과하는 조합이다. 참고 문서가 없으면 21개, 1개면 48개, 2개 이상이면 40개다(고정 양식은 참고 문서가 정확히 1개일 때만 연다). 원문 필요 여부는 규칙(`inferred_requires_source`)으로 정해지지 않는 `document-create`일 때만 true를 둔다. `template`은 규칙이 정해 분류값을 쓰지 않는다. 라우팅과 같이 고정 무작위 순서로 섞고 응답 예산은 15초다.
  - 개발 중 실측(2026-10-27, 문장마다 1회): 프롬프트 예시 12문장 LLM(Claude Haiku 4.5) 12/12·Jev 12/12, 예시 밖 5문장 LLM 5/5·Jev 4/5. Jev 오답은 표 변환 Skill에 `template`을 더한 건이다.
- **폴더 지목(추가):** 작업 탭 폴더 내용 조회(`folder_lookup`)에서 메시지가 지목한 폴더를 고른다. 설정은 `JEV_FOLDER_LOOKUP_ENABLED`(기본 `false`)이고 대체 경로는 LLM 판단(`prompts/agent_folder_lookup.system.md`)이다.
  - 선택지는 폴더 경로마다 하나, 이름이 같은 폴더가 여러 곳이면 그 이름 전부를 뜻하는 묶음 하나, `지목 없음`이다. Jev는 하나만 고르므로 같은 이름을 가릴 단서가 없으면 묶음을 골라 되묻게 한다. 라우팅과 같이 고정 무작위 순서로 섞는다.
  - 선택지가 255개를 넘으면 LLM 판단을 쓴다. 응답 예산은 라우팅과 같은 15초다.
  - 개발 중 12문장 실측(2026-10-27, 문장마다 1회): Jev 11/12, LLM(Claude Haiku 4.5) 12/12. Jev 오답은 `최상위 회의록 폴더`에서 묶음을 고른 건이다.

## Alternatives
- **Jev로 완전히 교체:** 크레딧이 없거나 장애가 나면 라우팅·질의·ingest가 함께 멈춘다. clarify와 hint 판정은 Jev가 대체하지 못한다.
- **요청 payload로 Jev 선택:** backend·Kafka 계약을 바꿔야 한다. 운영자가 배포 설정으로 켜고 끄는 용도에는 과하다.
- **설정 하나로 세 경로를 함께 켬:** 평가 근거의 강도가 경로마다 달라 단계적으로 켤 수 없다.
- **개념 후보를 BGE-M3로 추림(2026-10-29 채택):** 처음에는 ingest worker에 임베딩 모델(약 2.5GB)을 새로 올려야 해서(워커마다 모델을 올려 AI 노드 메모리를 넘던 문제, PR #39와 충돌) 기각했다. 임베딩 서버(`EMBEDDING_SERVICE_URL`)가 생겨 워커가 모델을 올리지 않아도 되므로 쌍 판정 후보에 쓴다. 임베딩 서버 설정이 없으면 Jev 개념 병합을 쓰지 않는다. 편입 워커가 임베딩 서버를 호출하려면 플랫폼 배포에서 `EMBEDDING_SERVICE_URL`과 NetworkPolicy 허용을 추가해야 한다.

## Consequences
- 평가와 달리 운영 요청에는 숫자 개인정보 마스킹과 LLM 보안 경계를 항상 적용한다(개념 병합 평가는 보안 경계 없이 측정했다).
- 기본값이 꺼짐이라 배포해도 동작은 바뀌지 않는다. 키를 Secrets Manager에 넣고 설정을 켜면 해당 경로만 Jev를 쓴다.
- 라우팅의 Jev route는 설명 대신 고정된 `reason`을 남긴다.
- 근거 선택은 관련 페이지 밖의 workspace 근거도 고를 수 있다. 질문마다 workspace unit을 모두 읽어 점수를 매긴다. 저장 벡터가 아직 없는 unit은 질문 시점에 임베딩하지 않고 dense 점수를 0으로 둔다(lexical 점수는 하이브리드가 전체 후보 기준으로 따로 넣는다). 벡터가 없는 unit만 BM25로 대신하면 그 안에서만 최댓값 정규화돼 관련성과 상관없이 1.0이 나오고 BM25가 이중으로 들어간다.
- 개념 후보에 임베딩 점수가 들어가 표기가 전혀 다른 동의어(한영 번역 등)도 후보에 든다. 개념 하나에 후보 수만큼 질문을 보내므로 요청 수·비용이 이전(질문 하나)보다 크다. 후보 100개면 요청 약 3개, 약 1.5만 토큰이다(짧은 정의 기준 오프라인 추정. 보안 경계를 질문마다 붙이던 때는 약 3.9만 토큰).
- 실제 Wiki 규모의 정확도·비용 곡선과 E2E 비용은 아직 측정하지 않았다. 켜기 전에 확인한다.
