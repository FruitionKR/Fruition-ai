# 0043. 편집 요청의 세부는 단어 대신 2단계 분류로 정한다

## 맥락
AI편집에서 "연구실 세미나 회의록을 반영해서 발표 구성의 각 항목 아래에 준비할 내용을 한 줄씩 채워줘"가 "편집안을 만들지 못했습니다"로 끝났다(2026-11-02 사용자 피드백). 실제 문서로 재현하니 두 번 시도 모두 출력 검사가 `## 논의 사항`·`## 결정 사항`·`## 다음 작업`이 없다고 막았다.

- 라우터는 대분류만 정한다. `edit_goal`의 `convert_format` 하나에 번호 목록·회의록·표·인용문·제목·코드·수식·Mermaid가 묶여 있고, 굵게·기울임 같은 서식은 받을 칸이 없다.
- 빠진 세부는 출력 검사 코드와 편집 프롬프트가 요청 문장의 단어로 각자 추측했다. 요청 문장에 "회의록"이 있으면 회의록으로 바꾸는 요청으로 보고, "추가"가 있으면 기존 줄을 모두 남기라고 요구하고, "표"와 "수정"이 함께 있으면 보호 조각을 풀었다. 번역 목표 언어도 "영어"·"한국어"라는 단어로 정했다.
- 단어는 문장에서 맡는 역할(결과 형식인지, 참고 자료인지, 유지하라는 대상인지)을 구분하지 못한다. 이 검사 파일의 최근 수정 대부분이 단어 검사의 예외를 더하는 일이었다.
- 같은 검사가 편집기가 빈 줄로 저장한 `<br />`도 막아서, 원문을 그대로 옮긴 결과가 첫 시도에서 실패했다(별도 커밋에서 원문에 있던 HTML은 허용하도록 고쳤다).

## 결정
1. **편집 세부 분류를 라우팅 2단계로 둔다.** 라우터가 편집으로 고른 요청은 편집기가 편집안을 만들기 전에 세부 분류기(`prompts/markdown_edit_detail.system.md`)를 한 번 더 부른다. 세부 분류기는 요청 문장, 대화 요약, 실행 중인 Skill 지침만 읽고 다음을 정한다(Skill만 실행하는 요청은 결과 형식이 지침에 있다).
   - `requested_formats`: 결과가 갖춰야 할 형식(`meeting_notes`, `table`, `numbered_list`, `blockquote`, `heading`, `inline_style`, `display_math`, `mermaid`, `code_block`).
   - `addition_only`: 기존 줄은 그대로 두고 추가만 하는 요청인지.
   - `structure_change`: 표·목록·제목·코드·수식·링크 같은 Markdown 구조를 바꾸는 요청인지.
   - `target_language`: 번역 목표 언어.
2. **라우터의 `edit_goal`은 세부 분류기에 넘기지 않는다.** 대분류 판단이 틀려도 세부 분류가 그 판단에 끌려가지 않고 문장을 따로 읽게 한다.
3. **코드는 요청 문장을 해석하지 않는다.** 출력 검사, 수식 보정, 보호 조각 해제, 원문 범위 편집 여부, 번역 필수 구간은 `edit_goal`·`edit_operation`과 세부 분류 값만 본다. 요청 문장의 단어 목록(`_asks_for_*`, `*_WORDS`)은 지운다.
4. **편집 프롬프트도 단어 대응 규칙을 지우고** `requested_formats`·`addition_only`를 받아 따른다.
4-1. **원문 HTML 허용량은 실제 교체 범위의 HTML만이다.** 앞뒤 문맥의 `<br />`를 복제하거나 삽입(`insert_after`)으로 HTML을 넣으면 새 HTML로 막는다.
4-3. **목록 형식 검사는 요청한 목록이 결과에 있는지만 본다.** 체크리스트·글머리표·번호 목록 항목이 하나도 없으면 막고, 다른 줄이 섞였는지는 LLM 평가기가 판단한다(2026-11-05). 줄마다 요구하면 도입 문장이나 표가 한 줄만 있어도 어떤 결과도 통과하지 못했다.
4-2. **섹션 제목은 구조를 바꾸지 않는 편집에서 잠근다.** 섹션 단위(`current_section`)로 정리·문체·줄이기를 할 때 `structure_change`가 거짓이고 `requested_formats`에 `heading`이 없으면, 섹션 맨 위 제목 줄을 보호 토큰으로 가린다. 결과 검사는 그 줄이 결과의 첫 줄로 그대로 남았는지 본다(하위 제목 `### 설치 방법`이 `## 설치`를 글자로 품을 수 있어 개수로 세지 않는다). 같은 형식 안에서 끊긴 줄을 잇는 요청은 구조 변경이 아니다.
5. **세부 분류가 실패하면(형식 오류·provider 통신 오류) 세부 요구가 없는 것으로 본다.** 형식 검사를 건너뛰고 LLM 평가기가 요청 충족 여부를 판단한다. 편집 자체는 막지 않는다.
6. **세부 분류는 Jev로 판정한다.** 라우팅 1단계와 같이 닫힌 값 중에서 고르는 판단이라 Jev가 맡는다. `JEV_EDIT_DETAIL_ENABLED`(기본 `false`)와 `TYPESAFE_API_KEY`가 있을 때만 쓰고, 꺼져 있거나 Jev 호출이 실패하면 편집과 같은 모델로 기존 LLM 분류를 한다. 호출 방식은 [ADR-0027](0027-jev-selective-judge.md)을 따른다.

## 대안과 기각 사유
- **단어 목록을 더 정교하게(예: "회의록으로", "회의록 형식"만 인정):** 같은 문제를 다른 표현에서 반복한다.
- **라우터 응답에 세부 칸 추가:** 호출은 늘지 않지만, 라우터가 대분류와 세부를 한 번에 판단하다 틀리면 그 값이 편집 모델과 검사에 그대로 전달된다. 세부만 따로 보는 단계를 두는 쪽이 정확하다고 보고 지연을 감수했다.
- **임베딩 유사도로 세부 분류:** 임베딩은 문장에 어떤 주제·단어가 있는지에 강하고 그 단어의 역할 구분에 약하다. "회의록을 참고해서 표로"와 "회의록으로 정리해줘"가 가깝게 나온다.
- **형식 검사를 모두 지우고 LLM 평가기에만 맡기기:** 회의록 제목·`$$`·표 구분선 같은 확정적인 모양 검사를 잃는다.

## 결과
- 편집 한 번에 분류 호출이 1회 늘어난다. Jev를 켜면 Jev 1회, 끄면 LLM 1회, Jev가 실패하면 둘 다 1회다. 출력이 짧은 분류라 편집 호출보다 빠르다.
- Jev 판정과 LLM(gpt-6-luna)을 2026-11-05에 비교했다. 건당 중앙값은 Jev 0.19초, LLM 2.03초다.
  - 분류(최종 코드): 기존 평가셋 25건은 3회 모두 75/75로 같다. 임시 문장 24건(작성자가 쓰고 선택지를 고르는 데도 썼다, 팀 검수 전, 저장소 밖)은 Jev와 LLM 모두 70/72다. 편집 요청 30건 문장에서 3회 분류가 어긋난 것은 구조 변경 값이 흔들린 2건뿐이다.
  - 실제 편집 30건 × 3회(Claude 채점, PR #217 없는 코드): 최종 코드는 세부 분류 Jev와 LLM 모두 82/90이다(사례 4건에서 달랐고 2:2). 형식 1개·목록 검사 완화 전에는 Jev 75/90, LLM 77/90이었다. 완화 전후 차이는 사례 단위로 5:1(부호검정 p=0.22)이라 개선으로 단정하지 않는다. 최종 코드의 체크리스트·글머리표 결과에서 다른 목록 항목이 섞인 사례는 없었다.
  - 형식마다 예/아니오로 물으면 수식 블록에 코드 블록까지 고르는 실패가 회차마다 났다. 선택지에 정의가 없으면 링크·이미지 변경을 구조 변경으로 잡지 못했다.
  - 글머리표·체크리스트 자리가 없으면 "체크리스트로 바꿔줘"를 번호 목록으로 골라 라우터 목표의 검사와 충돌했다. 자리를 넣은 뒤 관련 12문장은 번호 목록을 고르지 않았다.
  - 형식은 Jev 기준 요청당 1개다. 편집 요청 30건에서 LLM이 2개 이상을 고른 사례가 없었고, 2개까지 받으면 수식 + 코드 블록처럼 어떤 결과도 통과하지 못하는 조합이 나왔다. 확률 문턱으로 여러 개를 고르는 방식은 필요한 형식(0.05~0.43)과 잘못된 형식(0.12~0.17)의 확률이 겹쳐 쓰지 않았다(86문장 1회). 나머지 형식은 편집 모델과 평가기가 요청 문장으로 본다.
  - 선택지 문구에 민감하다. 문구를 바꾸면 다시 잰다.
- 세부 분류 평가셋 `pipeline/evals/markdown_edit_detail.jsonl`(24건, 이후 25건, 형식을 결과로 요구하는 문장과 자료로 언급만 하는 문장의 대조 포함)에서 gpt-6-luna, gemini-3.5-flash-lite, claude-haiku-4-5가 모두 24건을 맞혔다(2026-11-02). 처음 정답의 `structure_change`는 새 형식으로 바꾸는 요청을 `false`로 적어 세 모델과 7건이 어긋났다. 이 값의 용도(보호 해제, 원문 범위 편집 제외)에 맞춰 정의를 "형식 변환도 구조 변경"으로 명확히 하고 정답을 고쳤다.
- 실제 문서(연구계획서 초안·세미나 회의록)로 재현하니 위 요청이 편집안을 만들고 `<br />`도 유지했다. "회의록을 참고해서 표로"는 회의록 형식을 요구받지 않는다.
- 세부 분류가 틀리면 편집 모델과 형식 검사가 함께 틀린다. LLM 평가기가 요청 문장을 직접 읽어 마지막으로 거른다. 세부 분류 평가셋을 늘려 오분류 빈도를 계속 본다.
- Jev 편집 평가(claude-haiku-4-5, 30건×3회)를 3번씩 돌렸다(2026-11-02). 변경 전 184/270, 처음 변경 후 162/270이었다. 떨어진 몫은 대부분 섹션을 고칠 때 모델이 맨 위 제목을 빼먹은 실패(edit-11, edit-08)였다. 이 실패는 변경 전에도 절반가량 났고, 편집 프롬프트 문구를 한 줄만 바꿔도 빈도가 크게 흔들렸다(edit-11 단독 반복 8회에서 0~5회 성공). 프롬프트 운에 맡기지 않도록 4-2의 제목 잠금을 넣었고, 결과는 178/270(edit-11·edit-08 각 9/9)이었다. 남은 차이는 표 변환에서 시각을 빠뜨리는 실패(edit-07)와 법조문 내용 손실 판정(edit-09, edit-27)으로, 변경 전에도 같은 사유로 실패하던 케이스다.
- "섹션 제목을 더 짧게 바꿔줘"를 세부 분류기가 `heading`으로 잡지 못하면 제목이 잠긴 채 편집된다. 평가셋에 제목 변경 문장을 늘려 본다.
